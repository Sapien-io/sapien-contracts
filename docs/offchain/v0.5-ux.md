# Sapien PoQ v0.5 — UX Lifecycle Map

This document maps the complete user experience lifecycle for each protocol role from a product design perspective. It defines the steps, required data, UI states, and transitions that a frontend must support to surface the full protocol lifecycle.

---

## 1. Roles Overview

| Role | Who | Goal |
|---|---|---|
| **Originator** | A person or agent funding a quality task | Get AI-generated data validated and quality-scored |
| **Contributor** | A person or agent doing the work | Claim data points, submit work, earn rewards |
| **Validator** | A person or agent reviewing work | Score contributions honestly, earn rewards |
| **Adapter** | A frontend or tooling developer | Earn fees by facilitating protocol interactions |

All roles share a common **Onboarding** flow before entering their role-specific lifecycle.

---

## 2. Shared: Onboarding Flow

Every user — regardless of role — must complete onboarding before interacting with the protocol. The protocol uses Coinbase Smart Wallet (ERC-4337), so onboarding is seedless and passkey-native.

### Steps

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Create Wallet** | Tap "Get Started", register a passkey (Face ID / Touch ID / security key) | None — passkey is generated on device | Full-screen onboarding modal with passkey prompt |
| 2 | **Fund Wallet** | Deposit SAPIEN tokens into their Smart Account | Token amount, source wallet or on-ramp | Deposit flow: amount input, balance display, confirmation |
| 3 | **Grant Session Key** | One-time passkey approval granting the Sapien server a scoped session key | None — user confirms a passkey prompt | Permission dialog explaining what the server can/cannot do |
| 4 | **Ready** | User is routed to the appropriate role dashboard | — | Dashboard landing with role selector or auto-detection |

### UX Notes

- **No seed phrase.** Wallet creation is a single biometric prompt. Never show mnemonic words.
- **Session key approval** should clearly explain: "This lets Sapien submit transactions on your behalf for claiming, contributing, and settling. You will always sign validation scores yourself."
- **Gas is invisible.** The Paymaster sponsors all gas. Never show gas fees, ETH balances, or gas estimation UIs.
- **Smart Account address** is the user's permanent identity. Display it (truncated) in the profile/settings area.

### State Diagram

```
[No Account] → Create Wallet → [Wallet Created]
                                      │
                              Fund Wallet (deposit tokens)
                                      │
                              [Wallet Funded]
                                      │
                              Grant Session Key
                                      │
                              [Onboarded — Ready]
```

## 3. Originator Lifecycle

The originator creates a quality task, funds it with reward tokens, and monitors the work as it progresses through contribution and validation.

### 3.1 Phase: Create Project

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Define Task** | Fill out project parameters | `consensusThreshold` (quality bar), `numberOfValidations` (how many reviewers per item), `minStakeToClaim` (contributor stake), `validatorRewardBps` (validator share of rewards), `requiredSkill` (optional skill gate), `minValidatorReputation` (optional rep gate) | Multi-step form or wizard. Use human-readable labels: "Quality threshold", "Reviews per item", etc. |
| 2 | **Review Config** | Confirm settings before on-chain creation | All project params in summary view | Confirmation card with all parameters displayed, editable before submit |
| 3 | **Create On-Chain** | Confirm transaction (session key handles submission) | `projectId` (generated), full config | Loading state → success toast with project ID |

**Data returned:** `projectId` (bytes32), `ProjectCreated` event.

### 3.2 Phase: Upload Data

Before funding, the originator must upload the data that contributors will work on. Each project has an S3 bucket path, and the uploaded data must conform to the expected structure for the task type.

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Select Data Source** | Choose files or a directory to upload | Local files or API-generated dataset | File picker / drag-and-drop upload zone |
| 2 | **Validate Structure** | Client-side validation ensures each data point matches the required schema for this task type | Task type schema, uploaded files | Validation progress bar with per-file pass/fail indicators. Show: "Validating 150 data points…" → "148 valid, 2 errors" |
| 3 | **Review Errors** | Fix or remove invalid data points before upload | List of validation errors with file name, field, and reason | Error table: file name, error description, "Remove" or "Fix" action per row |
| 4 | **Upload to S3** | Confirm upload of validated data points | `projectId`, validated files | Upload progress bar → success summary: "150 data points uploaded to project storage" |
| 5 | **Confirm Quantity** | Verify the uploaded count matches the intended data point quantity for funding | `uploadedCount` | Confirmation card: "150 data points uploaded. Proceed to fund project for 150 items?" |

**Validation rules per data point:**

| Check | Description | Error Example |
|---|---|---|
| Schema conformance | Each file matches the JSON schema for the task type (e.g., required fields, field types) | "Missing required field: `prompt`" |
| File format | Files must be in the expected format (e.g., `.json`) | "Invalid file type: `item_47.csv` — expected `.json`" |
| Naming convention | Files follow the expected naming pattern (e.g., `0.json`, `1.json`, … sequential indices) | "Unexpected filename: `final_draft.json` — expected `47.json`" |
| Size limits | Each data point must be under the maximum allowed size | "File `12.json` exceeds 1 MB limit" |
| No duplicates | No duplicate indices or content hashes | "Duplicate content detected: `3.json` and `7.json`" |

**UX Notes:**

- **Schema is task-type specific.** The frontend should fetch the expected schema for the project's task type and validate client-side before uploading. Show the schema requirements in a collapsible "Data format requirements" section.
- **Quantity alignment.** The number of valid uploaded data points sets the upper bound for the quantity in the Fund step. The UI should carry this count forward automatically.
- **Re-upload supported.** Originators can replace or append data points before funding. After funding, the data is locked.
- **S3 path convention.** Data is stored at `s3://<bucket>/<projectId>/<index>.json`. The frontend handles path construction — the originator only sees a file upload interface.

### 3.3 Phase: Fund Project

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Set Reward Pool** | Enter total reward amount and data point quantity | `amount` (reward token amount), `qty` (number of data points), `adapter` address (auto-filled by frontend) | Amount input with token selector, quantity input, reward-per-item calculation shown live |
| 2 | **Approve Tokens** | Approve SapienCore to spend reward tokens | `amount` | ERC-20 approval prompt (can be batched with funding in a single UserOp) |
| 3 | **Fund** | Confirm funding transaction | `projectId`, `amount`, `qty`, `adapter` | Loading state → success with fee breakdown |

**Fee breakdown to display:**

| Line Item | Calculation | Example (1000 USDC) |
|---|---|---|
| Protocol fee | 10% of total | 100.00 USDC |
| Origination adapter fee | 4% of remainder | 36.00 USDC |
| **Net project escrow** | Remainder | **864.00 USDC** |
| Reward per data point | Escrow / quantity | Varies by qty |

**Data returned:** `ProjectFunded` event, `OriginationFeePaid` event, indices pushed to available stack.

### 3.4 Phase: Monitor Progress

The originator does not take further on-chain actions. Their experience is read-only monitoring.

| Data Point | Source | UI Element |
|---|---|---|
| Total data points | `project.totalQuantity` | Progress bar header |
| Available (unclaimed) slots | `project.availableSlots` | Segment of progress bar |
| Reserved (claimed, not yet submitted) | Count of `IndexState.status == Reserved` | Segment of progress bar |
| Submitted (pending validation) | Count of `IndexState.status == Submitted` | Segment of progress bar |
| Accepted | Count of `IndexState.status == Accepted` | Segment of progress bar (green) |
| Rejected (re-entered pool) | Tracked via `ConsensusReached` events with rejected status | Counter or log |
| Escrow remaining | `projectEscrow[projectId][token]` | Balance display |
| Reward pool utilization | Distributed / total | Percentage or bar |

### 3.5 Originator State Diagram

```
[Create Project] → [Project Created — No Data]
                          │
                    Upload Data
                    (validate & upload to S3)
                          │
                   [Data Uploaded — Unfunded]
                          │
                    Fund Project
                          │
                   [Project Active]
                     │         │
            Monitor Progress   │
             (read-only)       │
                     │         │
              [All Items       [Project Paused/
               Completed]       Cancelled]
```

### 3.6 Key UX Decisions

- **Wizard vs. single form:** Use a stepped wizard for project creation. Each step should explain the parameter in plain language with sensible defaults.
- **Upload before fund.** The originator uploads and validates data before committing funds. This ensures the data point count is accurate and the data is well-formed before any tokens are escrowed.
- **Client-side validation is a must.** Validate data structure, schema, naming, and size locally before uploading. Catching errors early prevents failed uploads and wasted time.
- **Live cost preview:** Show "Reward per data point" dynamically as the originator adjusts amount and quantity.
- **Progress dashboard:** The originator's primary post-funding view is a real-time dashboard showing the funnel from unclaimed → reserved → submitted → accepted.
- **No manual intervention needed.** The originator does not need to trigger consensus, settle validators, or manage claims. Keepers handle this automatically.

## 4. Contributor Lifecycle

The contributor claims data points, does off-chain work, and submits results. Their stake is locked during active claims and released (or slashed) based on completion.

### 4.1 Phase: Stake & Prepare

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Deposit to Vault** | Deposit SAPIEN tokens into SapienVault | `amount` (tokens to deposit) | Deposit flow with balance display, vault share preview |
| 2 | **Browse Projects** | View available projects and their requirements | List of active projects with: reward per item, slots available, required skill, min stake per slot, validator reward %, consensus threshold | Project cards or table with filters (skill, reward size, availability) |

### 4.2 Phase: Claim Indices

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Select Project** | Choose a project to contribute to | `projectId` | Project detail page |
| 2 | **Choose Quantity** | Decide how many data points to claim | `qty` (limited by available slots and affordable stake: `qty * minStakeToClaim <= available balance`) | Quantity selector with: max claimable shown, total stake lock shown, deadline shown |
| 3 | **Claim** | Confirm claim transaction (server submits via session key) | `projectId`, `qty`, `adapter` (auto-filled) | Loading state → success with assigned indices list |

**Data returned:** `claimId`, `indices[]` (from `ClaimCreated` event). The indices tell the contributor exactly which off-chain data points to work on (e.g., `47.json`, `91.json`).

**Post-claim state:**

| Field | Value |
|---|---|
| `claim.status` | Active |
| `claim.deadline` | Timestamp (shown as countdown) |
| `claim.submittedCount` | 0 |
| `claim.totalCount` | qty |
| Stake locked | `qty * minStakeToClaim` |

### 4.3 Phase: Work & Submit

This phase alternates between off-chain work and on-chain submission. The contributor works on each assigned index individually.

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **View Assignment** | See the list of assigned indices with their status | `claim.indices[]`, each index's `SubmissionStatus` | Checklist or kanban of indices: Reserved (to-do), Submitted (done) |
| 2 | **Do Work (off-chain)** | Complete the data point (e.g., label data, review AI output, write content) | Off-chain data identified by index (e.g., `47.json` fetched from IPFS/API) | Work interface specific to the task type — this is the adapter's responsibility |
| 3 | **Submit** | Submit the completed work on-chain | `claimId`, `index`, `submissionHash` (hash of off-chain work) | Per-index submit button, progress updates on checklist |
| 4 | **Repeat** | Continue until all indices are submitted or deadline approaches | — | Progress indicator: "3 of 5 submitted" |

**Batching note:** If the contributor completes multiple items, the adapter can batch multiple `contribute()` calls into a single UserOp. The UI should support "Submit All Ready" as a batch action.

### 4.4 Phase: Await Validation & Claim Rewards

After submission, the contributor waits for validators to score their work and consensus to be computed.

| # | Step | What Happens | Data to Display | UI Element |
|---|---|---|---|---|
| 1 | **Pending Validation** | Validators are committing and revealing scores | Number of reveals received vs. required (`revealCount / numberOfValidations`) | Per-index progress indicator: "2 of 3 reviews complete" |
| 2 | **Consensus Computed** | Keeper calls `computeConsensus` | Consensus result: `weightedAverage`, `Accepted` or `Rejected` | Status badge per index: green checkmark (accepted) or red X (rejected) |
| 3 | **Challenge Period** (if accepted) | Waiting period before reward release | `challengeEndsAt` countdown | Timer: "Reward available in 2h 14m" |
| 4 | **Release Reward** | Call `releaseContributorReward` (server can do via session key) | `projectId`, `index` | "Claim Reward" button (or auto-triggered by server) |
| 5 | **Claim Reward** | Call `claimReward(token)` to withdraw | `token` address | "Withdraw" button on rewards dashboard |

**If rejected:**

| Event | What Happens | UI |
|---|---|---|
| Contribution rejected | Index returns to available pool, nonce increments | Status badge turns red, "Rejected — score: X" |
| Reputation hit | -50 bps | Reputation change indicator (e.g., small red arrow) |
| Index re-enters pool | Another contributor can claim it | Index disappears from contributor's active list |

### 4.5 Phase: Expiry Path (Incomplete Claims)

If the contributor fails to submit all claimed indices before the deadline:

| Event | What Happens | UI |
|---|---|---|
| Deadline passes | Keeper calls `expireClaim(claimId)` | Status changes to "Expired" with warning styling |
| Unsubmitted indices returned | Pushed back to available stack | Indices marked "Returned" in grey |
| Partial slash | `minStake * unsubmittedCount` slashed | Slash amount shown: "-X SAPIEN slashed" |
| Submitted indices survive | Continue through validation pipeline | Submitted items remain in "Pending Validation" |
| Remaining stake unlocked | Contributor can withdraw | Balance updates |

### 4.6 Contributor State Diagram

```
[Browse Projects] → Select Project → [Project Detail]
                                           │
                                     Claim Indices
                                           │
                                   [Claim Active]
                                    │            │
                             Work on Index    Deadline
                                    │         Approaching
                                    │            │
                              Submit Work    [Claim Expired]
                                    │         ├─ Unsubmitted → returned
                                    │         ├─ Partial slash
                                    │         └─ Submitted → continue
                              [Submitted]
                                    │
                           Await Validation
                                    │
                        ┌───────────┴───────────┐
                   [Accepted]              [Rejected]
                        │                       │
                  Challenge Period          Rep penalty
                        │                  Index re-pools
                  Release Reward
                        │
                  Claim Reward
                        │
                  [Funds Withdrawn]
```

### 4.7 Key UX Decisions

- **Deadline visibility is critical.** Show a persistent countdown timer on every active claim. Use warning colors (yellow → red) as deadline approaches.
- **Index checklist pattern.** Each claimed index should be a discrete, trackable item in a checklist or kanban board. Status: To-Do → In Progress → Submitted → Accepted/Rejected.
- **Batch submission.** Let contributors submit multiple completed items at once.
- **Auto-release rewards.** The server should auto-call `releaseContributorReward` after the challenge period. The contributor should only need to manually claim if they want to withdraw.
- **Slash warnings.** Before a contributor claims indices, clearly show: "If you don't submit all X items by [deadline], you'll be slashed Y SAPIEN per unsubmitted item."

## 5. Validator Lifecycle

The validator reviews submitted contributions, scores them via commit-reveal, and earns rewards for accurate scoring. This is the most interaction-heavy role because commit and reveal require passkey signatures.

### 5.1 Phase: Stake & Lock Capacity

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Deposit to Vault** | Deposit SAPIEN tokens into SapienVault | `amount` | Deposit flow (same as contributor) |
| 2 | **Lock Validator Capacity** | Allocate a portion of vault balance to validation capacity via `lockValidatorCapacity` | `amount` (tokens to allocate to capacity pool) | Slider or input: "Allocate X SAPIEN for validation capacity". Show: capacity determines how many concurrent validations you can perform |

**Capacity explained to user:** "Your validation capacity determines how much stake you can put behind your scores. Higher capacity = more validations you can participate in simultaneously."

### 5.2 Phase: Browse & Claim Validation Work

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Browse Available Validations** | View contributions pending validation | List of projects with pending contributions: project skill requirements, minimum reputation required, reward per validation, number of reviews still needed | Filterable list of validation opportunities |
| 2 | **Claim Validation** | Claim one or more contributions to review (server submits via session key) | `projectId`, `indices[]` (contribution indices to validate) | "Claim to Validate" button on a pending contribution card |

**Data returned:** The validation claim ID and indices to validate (`ValidationClaimCreated` event). The validator now knows which off-chain data points and contributions to review.

**Gate checks (shown before claim):**

| Requirement | Data Source | UI |
|---|---|---|
| Required skill | `project.requiredSkill` | Skill badge — grey if unmet, green if met |
| Minimum reputation | `project.minValidatorReputation` | Rep score display — "Your reputation: 6200 / required: 5000" |
| Available capacity | `stakeAccount.validatorCapacity` | "Available capacity: X SAPIEN" |

### 5.3 Phase: Review & Score (Off-Chain)

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Review Contribution** | Examine the off-chain data point and the contributor's submission | Off-chain data (e.g., `47.json`), contributor's submission (identified by `submissionHash`) | Review interface: side-by-side view of original data and submission, or task-specific review UI |
| 2 | **Assign Score** | Decide on a quality score | Score (0–10000 basis points, or simplified to 0–100% in UI) | Score input: slider (0–100%), numeric input, or rubric-based scoring |
| 3 | **Choose Stake Amount** | Decide how much stake to put behind this score (confidence signal) | `stakeAmount` (from available capacity) | Stake input with guidance: "Higher stake = more weight in consensus, but more at risk if you're an outlier" |

### 5.4 Phase: Commit (Passkey Required)

This step **requires the user's passkey signature** — the server cannot do this on the validator's behalf. The UI must make this clear.

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Generate Commit** | Client-side: compute `commitHash = keccak256(abi.encodePacked(score, salt))` | `score`, `stakeAmount`, `salt` (random, generated client-side) | Automatic — computed in background. Show: "Your score is encrypted before submission" |
| 2 | **Sign & Submit Commit** | Passkey prompt to sign the UserOp containing `commitValidation` | Passkey biometric confirmation | Passkey modal: "Sign with Face ID to submit your encrypted score". Clearly indicate this is a security step the server cannot bypass |
| 3 | **Store Salt Locally** | Client stores `salt` securely for reveal phase | `salt`, `projectId`, `index` | Automatic — stored in local storage or secure enclave. Show: "Your reveal key has been saved" |

**Critical UX constraint:** The `salt` must be persisted on the client until reveal. If the user clears browser data or switches devices before revealing, they lose their commit and may be slashed. The UI should:

- Warn: "Do not clear browser data until you've completed the reveal step"
- Offer salt backup/export option
- Show pending commits prominently with "Reveal Required" status

**Post-commit state:**

| Field | Value |
|---|---|
| Commit hash stored on-chain | `commitHash` at `[projectId][index][nonce][validator]` |
| Stake moved | `capacity → inFlight` |
| Status | "Committed — awaiting reveal window" |

### 5.5 Phase: Reveal (Passkey Required)

After all validators have committed (or the commit window closes), the reveal window opens. This also requires a passkey signature.

| # | Step | User Action | Data Required | UI Element |
|---|---|---|---|---|
| 1 | **Reveal Window Opens** | Notification that it's time to reveal | Reveal window timing | Push notification / banner: "Reveal window open — reveal your score now" |
| 2 | **Confirm Reveal** | Passkey prompt to sign the UserOp containing `revealValidation` | `projectId`, `index`, `score`, `salt` (retrieved from local storage) | Passkey modal: "Sign with Face ID to reveal your score". Show the score being revealed |
| 3 | **Reveal Confirmed** | On-chain verification that hash matches | — | Success state: "Score revealed: 82/100" |

**Post-reveal state:**

| Field | Value |
|---|---|
| Score visible on-chain | `score` at `[projectId][index][nonce][validator]` |
| Stake returned | `inFlight → capacity` |
| `revealCount` incremented | Closer to triggering consensus |

**Failure to reveal:**

| Scenario | Consequence | UI |
|---|---|---|
| Reveal window expires without reveal | Stake remains in `inFlight` (self-punishing — never returned) | Warning: "You missed the reveal window. Your staked X SAPIEN is forfeited." |
| Lost salt | Cannot produce valid reveal | Error state: "Unable to reveal — encryption key not found. Stake will be forfeited." |

### 5.6 Phase: Consensus & Settlement

After all required reveals, consensus is computed and each validator settles individually.

| # | Step | What Happens | Data to Display | UI Element |
|---|---|---|---|---|
| 1 | **Consensus Computed** | Keeper calls `computeConsensus` | `weightedAverage`, `stdDeviation`, your score vs. consensus | Result card: "Consensus: 78/100. Your score: 82/100. Status: Accurate" or "Outlier" |
| 2 | **Settle** | Call `settleValidator` (server can do via session key) | `projectId`, `index`, `nonce` | "Settle" button (or auto-settled by server) |
| 3 | **Outcome** | Reward credited or stake slashed | Reward amount or slash amount | Green: "+X USDC reward credited" / Red: "-X SAPIEN slashed" |
| 4 | **Claim Reward** | Call `claimReward(token)` | `token` | "Withdraw" button on rewards dashboard |

**Outlier tiers to communicate:**

| Deviation from Consensus | Slash Severity | UI Label |
|---|---|---|
| < 1.5σ | No slash (accurate) | "Accurate" — green |
| 1.5σ – 2σ | Mild slash | "Slightly off" — yellow |
| 2σ – 3σ | Moderate slash | "Outlier" — orange |
| 3σ – 5σ | Heavy slash | "Significant outlier" — red |
| > 5σ | Maximum slash | "Extreme outlier" — dark red |

### 5.7 Validator State Diagram

```
[Lock Capacity] → [Capacity Allocated]
                        │
                 Browse Validations
                        │
                 Claim Validation
                        │
               [Validation Claimed]
                        │
                Review Off-Chain Work
                        │
                 Assign Score + Stake
                        │
            ┌──── Commit (passkey sign) ────┐
            │                               │
     [Committed]                     [Commit Failed]
            │                          (retry)
     Reveal Window Opens
            │
     ┌──── Reveal (passkey sign) ────┐
     │                               │
[Revealed]                    [Missed Reveal]
     │                          Stake forfeited
     │
 Consensus Computed
     │
  ┌──┴──┐
  │     │
[Accurate]  [Outlier]
  │           │
Reward     Slash +
credited   Rep penalty
  │
Claim Reward
  │
[Funds Withdrawn]
```

### 5.8 Key UX Decisions

- **Two-signature flow is the hardest UX challenge.** Validators must sign twice (commit + reveal) with their passkey. Make this crystal clear with a progress stepper: "Step 1: Submit encrypted score → Step 2: Reveal score".
- **Salt persistence is critical.** The salt links commit to reveal. If it's lost, the validator is slashed. Use multiple persistence strategies (localStorage + indexedDB + optional cloud backup). Show a persistent "Pending Reveal" badge until reveal is complete.
- **Confidence-based staking.** Frame stake amount as "confidence": "How confident are you in this score?" with a suggested default. Higher stake = higher weight = higher reward if accurate, but higher loss if outlier.
- **Outlier risk education.** Before a validator's first commit, show an explainer: "Your score is compared against other reviewers. If your score is significantly different from the group consensus, you may lose some of your staked tokens."
- **Notification system required.** The reveal window is time-sensitive. Push notifications (or email/webhook) are essential to prevent missed reveals.
- **Auto-settle via server.** The server should automatically call `settleValidator` (or `forceSettleValidator` for unresponsive validators) once consensus is computed and the challenge period has elapsed. The validator should not need to remember to settle.

## 6. Adapter Lifecycle

Adapters are frontends, oracle connectors, or tooling that facilitate protocol interactions. Their lifecycle is passive — they earn fees by being the `adapter` address passed during protocol calls.

### 6.1 How Adapter Fees Are Earned

| Fee Type | When Earned | How Bound | Fee Rate |
|---|---|---|---|
| **Origination fee** | When an originator funds a project through the adapter's frontend | `adapter` param in `fundProject()` | 4% of post-protocol-fee amount |
| **Contribution fee** | When a contributor claims indices through the adapter | `adapter` param in `claimToContribute()` | 3% of contributor reward at release |
| **Validation fee** | When a validator claims a validation through the adapter | `adapter` param in `claimToValidate()` | 3% of validator reward at settlement |

### 6.2 Adapter Dashboard

| Data Point | Source | UI Element |
|---|---|---|
| Total fees earned (all time) | Sum of `pendingRewards` + claimed rewards from events | Lifetime earnings card |
| Pending fees (unclaimed) | `pendingRewards[adapterAddress][token]` | Claimable balance with "Withdraw" button |
| Projects facilitated | Count of unique `projectId`s where adapter was origination adapter | Counter |
| Claims facilitated | Count of `claimId`s where adapter was contribution adapter | Counter |
| Validations facilitated | Count of validation adapter bindings | Counter |
| Fee breakdown by type | Origination / contribution / validation split | Pie chart or segmented bar |

### 6.3 Adapter State Diagram

```
[Register Adapter Address] → [Adapter Active]
                                    │
                     Users interact via adapter frontend
                     (adapter address auto-passed in calls)
                                    │
                           Fees accumulate in pendingRewards
                                    │
                           [Fees Available]
                                    │
                           claimReward(token)
                                    │
                           [Funds Withdrawn]
```

### 6.4 Key UX Decisions

- **No registration required.** Any address can be an adapter. The frontend simply passes its own address as the `adapter` param.
- **Same `claimReward` function.** Adapters use the same withdrawal mechanism as contributors and validators.
- **Transparent fee display.** When a user interacts through an adapter frontend, show the exact current fee for that flow (default 4% origination, 3% contribution, 3% validation).

## 8. Shared: Reputation Display

Reputation is visible across the platform and affects participation eligibility.

### 8.1 Reputation Data

| Data Point | Source | UI Element |
|---|---|---|
| Current score | `reputation[user][role].score` | Score display: 0–100% (e.g., "62.0%"), with color coding (red < 30%, yellow 30–60%, green > 60%) |
| Role-specific scores | Separate reputation per role (originator, contributor, validator) | Tab or card per role |
| Trend | Computed from recent `ReputationUpdated` events | Sparkline or arrow (trending up/down/stable) |
| Total actions | `reputation.totalActions` | "X actions completed" |
| Success rate | `successfulActions / totalActions` | Percentage display |
| Daily gain remaining | `MAX_DAILY_GAIN - dailyGain` (if same UTC day) | "Daily gain remaining: 0.6%" |
| Decay status | Time since `lastUpdated` × `DECAY_RATE` | "Inactive decay: -0.2% pending" (only if inactive) |

### 8.2 Reputation UX Rules

- **Always show reputation near the user's identity.** It's a trust signal.
- **Explain asymmetry.** "+0.1% for success, -0.5% for rejection, -1.0% for slashing." Make clear that losing reputation is much easier than gaining it.
- **Gate visibility.** When a user doesn't meet the reputation requirement for a project, show the requirement and their current score side by side: "Required: 50% | Yours: 42%".
- **Decay nudge.** If a user hasn't been active, show: "Your reputation is decaying due to inactivity. Complete a task to stop decay."

## 11. Error States & Edge Cases

Every UI must handle these gracefully.

### 11.1 Contributor Errors

| Error | Cause | UI Treatment |
|---|---|---|
| `InsufficientStake` | Not enough vault balance to cover `minStake * qty` | Disable claim button, show: "Deposit X more SAPIEN to claim Y items" |
| `ClaimExpired` | Trying to submit after deadline | Show expired state, explain slash consequences |
| `IndexNotInClaim` | Submitting to an index not assigned to this claim | Should not happen in well-built UI — defensive error page |
| `NotClaimOwner` | Wrong account | Account mismatch warning |

### 11.2 Validator Errors

| Error | Cause | UI Treatment |
|---|---|---|
| `InsufficientReputation` | Below project's min reputation threshold | "Your reputation (X%) is below the required Y%. Complete more validations to increase it." |
| `InvalidReveal` | Hash mismatch (wrong salt, wrong score) | "Reveal failed — your encrypted score doesn't match. Check that you haven't changed devices." |
| `NonceMismatch` | Contribution was rejected and resubmitted between commit and reveal | "This contribution was resubmitted. Your validation is no longer valid." |
| `ConsensusNotReady` | Not enough reveals yet | "Waiting for X more reviewers before consensus can be computed." |
| `AlreadySettled` | Trying to settle twice | Idempotent — show "Already settled" |

### 11.3 Originator Errors

| Error | Cause | UI Treatment |
|---|---|---|
| Schema validation failed | One or more data points don't match the task type schema | Per-file error list: "47.json — missing required field: `prompt`". Disable upload until resolved |
| Upload failed | S3 upload error (network, permissions, size) | Retry button with error detail: "Upload failed for 3 files. Tap to retry." Resume from last successful file |
| Quantity mismatch | Funded quantity doesn't match uploaded data point count | Warning: "You uploaded 148 data points but are funding 150. Upload 2 more or reduce quantity." |
| `AdapterFeeTooHigh` | Configured fee exceeds 5% cap | Should not happen in UI — admin config issue |
| Insufficient token approval | Didn't approve enough for funding | "Please approve X tokens first" with approval button |

## 13. Progressive Disclosure Strategy

Not all complexity should be shown upfront. Layer the experience.

### Level 1: Essentials (shown to all users)

- Wallet balance and rewards
- Active tasks (claims, pending validations)
- Reputation score (single number)
- Simple action buttons ("Claim", "Submit", "Reveal")

### Level 2: Details (shown on expansion or drill-down)

- Stake breakdown (locked, capacity, in-flight, available)
- Fee breakdowns (protocol fee, adapter fee, net reward)
- Reputation history and trend
- Consensus details (weighted average, std deviation, your position)

### Level 3: Advanced (settings or power-user mode)

- Raw on-chain data (transaction hashes, block numbers)
- Adapter fee configuration
- Session key management
- Validator capacity fine-tuning
- Reputation decay parameters

## 14. Key Design Principles for the UI

| Principle | Rationale |
|---|---|
| **Gas is invisible** | Paymaster covers all gas. Never show gas fees, ETH requirements, or gas estimation UIs. |
| **One biometric = one action** | Passkey prompts should map 1:1 to meaningful user decisions. Don't prompt twice for the same logical action. |
| **Deadlines are first-class** | Every time-sensitive action (claim deadline, reveal window) gets a visible, persistent countdown. |
| **Pull, don't push** | The protocol uses pull-based reward claiming. The UI should make claiming easy but never auto-withdraw without consent. |
| **Explain slashing before it happens** | Every action that puts stake at risk should show the risk clearly before the user commits. |
| **Reputation is a first-class citizen** | Show it everywhere. It affects eligibility, weight, and earning potential. Make it feel like a score worth protecting. |
| **Progressive onboarding** | Don't dump all roles on a new user. Let them start as a contributor (simplest), then unlock validator and originator flows as they build reputation. |
| **Batch where possible** | Use UserOp batching to reduce the number of interactions. "Submit All" > submitting one by one. |
