# Sapien PoQ v0.5 — Design Specification

## 1. Problem Statement

Sapien PoQ is a decentralized quality oracle for AI workflows. It enables stake-weighted, consensus-based verification of AI-generated data and agent behaviors. Originators post tasks with funded reward pools, contributors claim specific data points and submit work, validators independently score that work via commit-reveal, and the protocol settles rewards and slashing based on weighted agreement. Participants may be human, AI agents, or hybrid teams.

---

## 2. Design Principles

| # | Principle | Rationale |
|---|-----------|-----------|
| 1 | On-chain minimalism | Only state that must be trustless lives on-chain. Queue management and deadline monitoring are keeper/indexer concerns. |
| 2 | No cross-contract calls in hot paths | Finalization currently does 5-15+ `CALL` opcodes. The redesign targets zero external calls during consensus computation. |
| 3 | Single source of truth | Every piece of state lives in exactly one place. No shadow bookkeeping, no manual sync. |
| 4 | Pull everywhere | Every participant pulls their own outcomes. No loops over validators inside a single transaction. |
| 5 | Phase separation | Consensus computation, validator settlement, and reward claiming are independent transactions. |
| 6 | Exclusive index assignment | Each on-chain index maps to a specific off-chain data point (e.g. `47.json`). Assignment must be exclusive and deterministic — no race conditions, no duplicated work. |
| 7 | Smart account native | All callers are ERC-4337 Smart Accounts (Coinbase Smart Wallet). No EOA assumptions (`tx.origin`, `ecrecover`). Delegation, batching, and gas sponsorship happen at the account layer, not the protocol layer. |

---

## 3. Architecture

### 3.1 Contract Topology

Two contracts and one library, down from five contracts:

```
QualityEngine (single contract)
├── Project management
├── Claim & index management
├── Contribution tracking
├── Validation state machine (commit-reveal)
├── Consensus computation (via library)
├── Reputation (inline)
├── Reward escrow & distribution (inline)
└── calls ──→ StakeVault (external, for stake operations only)

StakeVault (ERC-4626)
├── Deposits / withdrawals
├── Contributor locks
├── Validator capacity
├── In-flight stake tracking
└── Slashing (share burn)

ConsensusLib (library, linked via delegatecall)
├── Weighted average calculation
├── Standard deviation
├── Outlier detection
└── Tiered slash computation
```

### 3.2 Why Merge Core + Oracle + Trust + Rewards

| Current Contract | Why It Merges Into QualityEngine |
|---|---|
| `ValidationOracle` | Not a true oracle (doesn't bridge external data). It's the core validation state machine. Separating it from Core created duplicated project state and forced cross-contract calls during finalization. |
| `SapienTrust` | Read and written exclusively during finalization/settlement. Every reputation update as a cross-contract call adds ~3k gas overhead for no isolation benefit. |
| `Rewards` | A mapping with escrow semantics. No independent logic that justifies a separate contract and proxy. |

### 3.3 Why StakeVault Stays Separate

The vault holds user funds and implements ERC-4626. Keeping it separate provides:

- Independent audit surface for custody logic
- Clean upgrade boundary (vault upgrades don't touch protocol logic)
- Potential for the vault to serve multiple protocol versions

### 3.4 Upgradeability

- Both contracts deployed behind ERC-1967 proxies (same as today).
- `QualityEngine` uses ERC-7201 namespaced storage with separate namespaces per logical module (projects, claims, contributions, validations, reputation, rewards). This gives upgrade safety equivalent to separate contracts.
- Consensus algorithms remain pluggable via an `IConsensusAlgorithm` interface. This is the one allowed `staticcall` during consensus computation.
- If independent module upgradeability becomes critical, ERC-2535 (Diamond) is a future option — facets share storage but upgrade independently.

### 3.5 Account Abstraction Layer (ERC-4337 + Coinbase Smart Wallet)

All user interactions flow through ERC-4337 Smart Accounts. The protocol contracts are unaware of the account abstraction layer — they see `msg.sender` as the user's Smart Account address, which is stable and deterministic.

```
User (Passkey / WebAuthn)
    │
    ▼
Coinbase Smart Wallet (ERC-4337 Smart Account)
    │
    ├─ Owner: User's passkey (WebAuthn credential)
    ├─ Session Key: Sapien server (scoped, time-bounded)
    │   ├─ Allowed: claim, contribute, settle, reward, keeper functions
    │   └─ NOT allowed: commitValidation, revealValidation
    │
    ▼
EntryPoint (ERC-4337)
    │
    ├─ Paymaster (Sapien-operated, sponsors gas)
    │
    ▼
┌─────────────────────┐     ┌──────────────┐
│   QualityEngine     │────►│  StakeVault   │
│                     │     │  (ERC-4626)   │
│  Projects           │     │              │
│  Claims + Indices   │     │  Deposits    │
│  Contributions      │     │  Locks       │
│  Validations        │     │  Slashing    │
│  Consensus (lib)    │     └──────────────┘
│  Reputation         │
│  Rewards (escrow)   │
└─────────────────────┘
```

**Why Coinbase Smart Wallet, not ERC-8004 identity:**

The previous `docs-v0.4/architecture/8004/` plan explored a full identity-layer redesign with `AgentAccount`, `AgentForwarder`, `AgentIdentityResolver`, and re-keying all protocol state from `address` to `bytes32 agentKey`. The Coinbase Smart Wallet approach achieves the same user-facing goals with dramatically less protocol complexity:

| Concern | ERC-8004 approach | Coinbase Smart Wallet approach |
|---|---|---|
| Stable identity | `agentKey` derived from registry | Smart Account address (CREATE2 deterministic) |
| Signer rotation | Controller rotation via registry | Add/remove passkeys on Smart Account |
| Delegation | `AgentForwarder` + EIP-712 typed actions | Session keys on Smart Account |
| Recovery | Custom rotation invariants | Coinbase recovery service + social recovery |
| Protocol changes required | Re-key all state, new auth modules, resolver layer | None — protocol stays address-keyed |
| New contracts | ~13 new contracts (registries, adapters, resolver, forwarder, factory) | 0 new protocol contracts |
| Gas overhead | Forwarder + resolver indirection on every call | Zero — delegation resolved at account level |

The 8004 identity model can be layered on later as off-chain middleware (mapping Smart Account addresses to ERC-8004 identities for indexing/analytics) without touching protocol contracts.

**Server delegation model:**

The Sapien server receives a time-bounded session key on each user's Smart Account. This session key is scoped to specific contract function selectors. The server submits UserOperations to the Bundler on behalf of users. Gas is paid by a Sapien-operated Paymaster.

User onboarding flow:

1. User creates Coinbase Smart Wallet (passkey-based, no seed phrase).
2. User deposits SAPIEN tokens into their Smart Account.
3. User grants the Sapien server a session key scoped to QualityEngine + StakeVault functions (one-time passkey approval).
4. Server can now submit UserOps for all non-sensitive protocol interactions.
5. For validation commit/reveal, the user signs locally via passkey (see Section 5.3).

**Batching:**

ERC-4337 UserOperations natively support batched calls. The server can compose multi-call UserOps:

```
// Single UserOp: contributor claims (server passes its adapter address)
[
  qualityEngine.claimToContribute(projectId, 3, adapterAddress),
]

// Single UserOp: batch contribute after off-chain work
[
  qualityEngine.contribute(claimId, 12, hash1),
  qualityEngine.contribute(claimId, 47, hash2),
  qualityEngine.contribute(claimId, 91, hash3),
]

// Single UserOp: server as keeper batches consensus
[
  qualityEngine.computeConsensus(projA, index1),
  qualityEngine.computeConsensus(projA, index2),
  qualityEngine.computeConsensus(projB, index5),
]
```

Because batching is handled at the UserOp layer, the protocol contracts do **not** need batch convenience functions (`batchContribute`, `batchFinalize`, etc.). This simplifies the contract surface and eliminates `MAX_BATCH_SIZE` limits.

## 4. Data Model

### 4.1 StakeVault

```solidity
struct StakeAccount {
    uint256 contributorLock;    // locked for active contribution claims
    uint256 validatorCapacity;  // locked for validation capacity pool
    uint256 inFlight;           // committed-but-not-revealed validation stake
}

mapping(address => StakeAccount) accounts;
```

All lock categories live in the vault. No shadow bookkeeping elsewhere. The engine calls typed functions (`lockContributor`, `lockValidatorCapacity`, `commitStake`, `releaseCommit`, `slashContributor`, `slashValidator`) that manipulate the appropriate fields.

### 4.2 QualityEngine — Projects

```solidity
struct Project {
    address originator;
    IERC20  rewardToken;
    uint256 totalRewards;           // total funded (after fees)
    uint256 totalQuantity;          // total data points
    uint256 availableSlots;         // claimable slots remaining
    uint256 consensusThreshold;     // score threshold for acceptance (basis points)
    uint256 minStakeToClaim;        // contributor stake requirement per slot
    uint256 validatorRewardBps;     // validator share of rewards (0-2500)
    uint256 numberOfValidations;    // required reveals per contribution
    bytes32 requiredSkill;          // optional skill gate
    uint256 minValidatorReputation; // optional reputation gate
    ProjectStatus status;
}

mapping(bytes32 => Project) projects;
```

Single source of truth. No duplication across contracts.

### 4.3 QualityEngine — Claims & Index Management

```solidity
struct Claim {
    address   claimant;
    bytes32   projectId;
    uint64    deadline;
    uint32    submittedCount;
    uint32    totalCount;
    ClaimStatus status;          // Active, Completed, Expired
    uint256[] indices;           // assigned indices stored in the claim
}

struct IndexState {
    address reservedBy;          // address(0) = available
    uint256 claimId;             // owning claim
    uint64  deadline;            // mirrors claim deadline
    SubmissionStatus status;     // Empty, Reserved, Submitted, Accepted, Rejected
}

mapping(uint256 => Claim) claims;
mapping(bytes32 => mapping(uint256 => IndexState)) indexStates;

// Available index stack (O(1) push/pop)
mapping(bytes32 => mapping(uint256 => uint256)) availableIndexStack;  // position => index
mapping(bytes32 => uint256) availableIndexTop;                        // stack pointer
```

Key design decision: indices are stored in the `Claim` struct so that expiry can atomically return unsubmitted indices to the available stack. No zombie indices, no separate reclamation call.

### 4.4 QualityEngine — Contributions

```solidity
struct Contribution {
    address contributor;
    bytes32 submissionHash;
    uint256 rewardRate;          // snapshot at submission time (anti-sandwich)
    uint64  submittedAt;
    uint64  challengeEndsAt;     // nonzero after acceptance
    ContributionStatus status;   // Pending, Accepted, Rejected
}

mapping(bytes32 => mapping(uint256 => Contribution)) contributions;
```

No `projectId` in the struct (redundant with mapping key).

### 4.5 QualityEngine — Validations

```solidity
// Nonce tracks re-submissions. When a contribution is rejected and the index
// re-enters the pool, the nonce increments, invalidating stale commits/reveals.
mapping(bytes32 => mapping(uint256 => uint256)) submissionNonce;

// Commits: keyed by (projectId, index, nonce, validator) — O(1) access
mapping(bytes32 => mapping(uint256 => mapping(uint256 => mapping(address => bytes32)))) commitHashes;
mapping(bytes32 => mapping(uint256 => mapping(uint256 => mapping(address => uint64))))  commitTimestamps;

// Reveals: keyed the same way
struct Reveal {
    uint16  score;
    uint128 stakeAmount;
    uint64  revealedAt;
}
mapping(bytes32 => mapping(uint256 => mapping(uint256 => mapping(address => Reveal)))) reveals;

// Tracking how many reveals exist for the current nonce
mapping(bytes32 => mapping(uint256 => mapping(uint256 => uint256))) revealCount;

// Validator list per (projectId, index, nonce) — needed for consensus iteration
mapping(bytes32 => mapping(uint256 => mapping(uint256 => address[]))) revealedValidators;
```

No growing arrays that accumulate across nonces. Each nonce gets its own clean namespace. Old nonce data becomes dead storage (costs nothing to leave, no iteration over it).

**Commit-reveal integrity under delegation (critical constraint):**

The commit-reveal scheme prevents herding — validators must commit their score before seeing others' scores. If the Sapien server has full delegation authority and constructs transactions on behalf of validators, the server would know the score at commit time. This could allow the server to selectively delay or censor commits, or leak scores between validators.

Session key scoping must enforce this boundary:

| Operation | Server session key | User passkey required | Reason |
|---|---|---|---|
| `setValidatorCapacity` | Allowed | — | No privacy concern |
| `claimToValidate` | Allowed | — | No privacy concern |
| `commitValidation` | **Not allowed** | **Required** | Server must not see score inside commit hash |
| `revealValidation` | **Not allowed** | **Required** | Server must not see plaintext score before reveal window |
| `settleValidator` | Allowed | — | Post-consensus, no privacy concern |

For `commitValidation` and `revealValidation`, the validator's client (browser or AI agent) constructs the full calldata locally, signs the UserOperation with their passkey, and the server relays it to the Bundler without inspecting the calldata. The Smart Account validates the passkey signature; the server only sees an opaque signed UserOp.

### 4.6 QualityEngine — Consensus Reports (Cached)

```solidity
struct ConsensusReport {
    uint256 weightedAverage;
    uint256 stdDeviation;
    uint256 nonce;                            // which submission nonce this covers
    bool    computed;
    mapping(address => bool)    isOutlier;
    mapping(address => uint256) slashAmount;
    mapping(address => uint256) weight;       // consensus weight (used for reward distribution)
    mapping(address => bool)    settled;      // whether this validator has pulled their outcome
    uint256 totalAccurateWeight;              // sum of weights for non-outlier validators
}

mapping(bytes32 => mapping(uint256 => ConsensusReport)) consensusReports;
```

Computed once, read many times. Never recomputed.

### 4.7 QualityEngine — Reputation (Inline)

```solidity
struct Reputation {
    uint256 score;              // 0-10000 basis points, default 5000
    uint256 totalActions;
    uint256 successfulActions;
    uint256 lastUpdated;        // for lazy decay
    uint256 dailyGain;          // accumulated gain for current UTC day
    uint256 dailyGainDate;      // which UTC day the dailyGain applies to
}

mapping(address => mapping(bytes32 => Reputation)) reputation;  // user => role => rep
```

Same mechanics as current `SapienTrust`: asymmetric gains/losses, lazy decay, daily gain cap, per-role tracking. Implemented as `internal` functions instead of cross-contract calls.

### 4.8 QualityEngine — Rewards (Inline Escrow)

```solidity
// Project-level escrow (funded by originator, distributed to participants)
mapping(bytes32 => mapping(address => uint256)) projectEscrow;  // projectId => token => balance

// Per-user pending rewards (accumulated from multiple projects)
mapping(address => mapping(address => uint256)) pendingRewards;  // user => token => amount
```

Two mappings replace the entire `Rewards` contract. `distributeReward` is an internal function that decrements escrow and increments pending. `claimReward` transfers and zeroes. Adapter fees are also credited to `pendingRewards` (adapters claim via the same `claimReward` function as participants).

### 4.9 QualityEngine — Adapter Fees

Adapter fees reward the developers who build frontends, oracle adapters, and off-chain tooling that facilitate protocol interactions. There are three fee layers, each bound at the point where the adapter provides value:

```solidity
// ---- Fee configuration (admin-set, global) ----

uint256 constant MAX_ADAPTER_FEE_BPS = 500;  // 5% hard cap per layer

uint256 originationFeeBps;    // default 200 (2%) — paid by originator at funding time
uint256 contributionFeeBps;   // default 200 (2%) — deducted from contributor reward at release
uint256 validationFeeBps;     // default 200 (2%) — deducted from validator reward at settlement

// ---- Per-action adapter bindings ----

// Origination adapter: the frontend that helped the originator create/fund the project
mapping(bytes32 => address) originationAdapter;  // projectId => adapter

// Contribution adapter: the frontend/oracle adapter that helped the contributor claim and submit work
mapping(uint256 => address) contributionAdapter;  // claimId => adapter

// Validation adapter: the oracle adapter that helped the validator claim and validate work
// Keyed by (projectId, index, nonce, validator) — same namespace as validation state
mapping(bytes32 => mapping(uint256 => mapping(uint256 => mapping(address => address)))) validationAdapter;
```

**Fee waterfall:**

```
Originator funds 1000 USDC
│
├─ Protocol fee (1%)       →  10 USDC  → treasury
├─ Origination fee (2%)    →  19.80 USDC → origination adapter
└─ Project escrow          → 970.20 USDC
    │
    ├─ Contributor reward released (per slot)
    │   ├─ Contribution adapter fee (2% of reward) → contribution adapter
    │   └─ Net reward → contributor's pendingRewards
    │
    └─ Validator reward settled (per validator)
        ├─ Validation adapter fee (2% of reward)   → validation adapter
        └─ Net reward → validator's pendingRewards
```

**Key design decisions:**

- **Adapter bound at action time, not claim time.** The adapter address is recorded when the adapter provides value (funding, claiming, validating), not when the participant claims their reward. This prevents griefing (claiming with a different adapter address) and guarantees the adapter its fee.
- **Adapter fees accumulate in `pendingRewards`.** Adapters use the same `claimReward(token)` function as participants. No separate claiming mechanism.
- **No adapter = no fee.** If `adapter == address(0)`, no fee is deducted. Direct protocol interactions without an adapter pay no adapter fee.
- **Fee rates are global, not per-adapter.** All adapters receive the same percentage. This keeps the model simple and avoids a registration/whitelisting mechanism.

### 5.4 Phase 4: Finalization (Three Independent Steps)

This is the critical redesign. Today's single atomic transaction becomes three independent phases.

**Step 1: Compute Consensus** (anyone can call, computed once, cached)

```
Anyone                                  QualityEngine
    │                                        │
    ├─ computeConsensus(projId, index) ─────►│
    │                                        ├─ verify revealCount >= numberOfValidations
    │                                        ├─ verify not already computed for this nonce
    │                                        │
    │                                        ├─ for each validator in revealedValidators:
    │                                        │    build ValidationInput {
    │                                        │      score, stakeAmount,
    │                                        │      reputation (internal read + lazy decay)
    │                                        │    }
    │                                        │
    │                                        ├─ ConsensusLib.calculate(inputs)  ← delegatecall
    │                                        │   (weighted average, stddev, outlier detection,
    │                                        │    tiered slash amounts, validator weights)
    │                                        │
    │                                        ├─ store ConsensusReport (cached forever)
    │                                        │   - weightedAverage, stdDeviation
    │                                        │   - isOutlier[validator], slashAmount[validator]
    │                                        │   - weight[validator], totalAccurateWeight
    │                                        │
    │                                        ├─ if weightedAverage >= threshold:
    │                                        │    contribution.status = Accepted
    │                                        │    contribution.challengeEndsAt = now + CHALLENGE
    │                                        │    _updateReputation(contributor, +, avgScore)
    │                                        │    indexState.status = Accepted
    │                                        │ else:
    │                                        │    contribution.status = Rejected
    │                                        │    _updateReputation(contributor, -, avgScore)
    │                                        │    submissionNonce++ (invalidates stale data)
    │                                        │    indexState.status = Empty
    │                                        │    push index back to available stack
    │                                        │    project.availableSlots++
    │                                        │
    │                                        ├─ emit ConsensusReached(projId, index, avg, status)
```

Gas cost: ~150k. Internal reads + library math + storage writes. **Zero external calls** (reputation is inline, consensus is a library).

**Step 2: Settle Validator** (each validator pulls their own outcome)

```
Validator                               QualityEngine                StakeVault
    │                                        │                           │
    ├─ settleValidator(projId, index) ──────►│                           │
    │                                        ├─ verify consensus computed│
    │                                        ├─ verify not already settled│
    │                                        ├─ mark settled[validator]  │
    │                                        │                           │
    │                                        ├─ if isOutlier[validator]: │
    │                                        │    slashValidator ───────►│
    │                                        │    (slashAmount)          │
    │                                        │    _updateReputation      │
    │                                        │    (validator, -, 0)      │
    │                                        │                           │
    │                                        ├─ else if Accepted:        │
    │                                        │    reward = totalRewards  │
    │                                        │      * validatorBps       │
    │                                        │      * weight[v]          │
    │                                        │      / (10000 * qty       │
    │                                        │        * totalAccWeight)  │
    │                                        │                           │
    │                                        │    // Validation adapter  │
    │                                        │    // fee deduction       │
    │                                        │    adapter = validation   │
    │                                        │      Adapter[p][i][n][v]  │
    │                                        │    if adapter != 0:       │
    │                                        │      fee = reward *       │
    │                                        │        validationFeeBps   │
    │                                        │        / 10000            │
    │                                        │      pendingRewards       │
    │                                        │        [adapter] += fee   │
    │                                        │      reward -= fee        │
    │                                        │                           │
    │                                        │    pendingRewards[v] +=   │
    │                                        │      reward               │
    │                                        │    _updateReputation      │
    │                                        │    (validator, +, 0)      │
    │                                        │                           │
    │                                        ├─ emit ValidatorSettled    │
```

Gas cost: ~80k per validator. Each validator is independently motivated to call this (it's how they unlock stake and earn rewards). If a validator never settles, their stake stays in `inFlight` — self-punishing.

**Step 3: Claim Reward** (universal, for both contributors and validators)

```
Participant                             QualityEngine
    │                                        │
    ├─ claimReward(token) ─────────────────►│
    │                                        ├─ amount = pendingRewards[sender][token]
    │                                        ├─ require amount > 0
    │                                        ├─ pendingRewards = 0
    │                                        ├─ IERC20(token).safeTransfer(sender, amount)
    │                                        ├─ emit RewardClaimed
```

For contributors, their reward is credited to `pendingRewards` after the challenge period elapses. A separate function handles this:

```
Contributor                             QualityEngine
    │                                        │
    ├─ releaseContributorReward              │
    │   (projId, index) ──────────────────►  │
    │                                        ├─ verify status == Accepted
    │                                        ├─ verify challengeEndsAt < now
    │                                        ├─ verify not already released
    │                                        ├─ reward = contribution.rewardRate
    │                                        ├─ projectEscrow -= reward
    │                                        │
    │                                        │  // Contribution adapter
    │                                        │  // fee deduction
    │                                        ├─ adapter = contributionAdapter
    │                                        │   [contribution.claimId]
    │                                        ├─ if adapter != address(0):
    │                                        │    fee = reward *
    │                                        │      contributionFeeBps / 10000
    │                                        │    pendingRewards[adapter] += fee
    │                                        │    reward -= fee
    │                                        │
    │                                        ├─ pendingRewards[contributor] += reward
    │                                        ├─ emit ContributorRewardReleased
    │                                        │
    ├─ claimReward(token) ─────────────────►│  (same universal claim)
```

## 6. Reputation System

Identical mechanics to current `SapienTrust`, implemented as internal functions.

### 6.1 Parameters

| Parameter | Value | Description |
|---|---|---|
| `DEFAULT_REPUTATION` | 5,000 | Starting score (50%) |
| `MAX_REPUTATION` | 10,000 | Ceiling (100%) |
| `MIN_REPUTATION` | 500 | Floor (5%) |
| `SUCCESS_INCREASE` | 10 | Base gain per success (+0.1%) |
| `REJECTION_DECREASE` | 50 | Penalty per rejection (-0.5%) |
| `SLASH_DECREASE` | 100 | Penalty per slash (-1%) |
| `MAX_DAILY_GAIN` | 100 | Daily gain cap (1%) |
| `MIN_REPUTATION_FLOOR` | 1,000 | Weight calculation floor (10%) |
| `DECAY_RATE` | configurable | Basis points per day (default 10) |

### 6.2 Consensus Weight

```
effectiveRep = max(reputation, MIN_REPUTATION_FLOOR)
weight = (stakeAmount * effectiveRep) / 10000
```

### 6.3 When Reputation Changes

| Trigger | Role | Direction | Amount |
|---|---|---|---|
| Project created | Originator | + | +10 bps |
| Contribution accepted | Contributor | + | +10 bps + quality bonus (up to +20) |
| Contribution rejected | Contributor | - | -50 bps |
| Accurate validation (settle) | Validator | + | +10 bps |
| Outlier validation (settle) | Validator | - | -100 bps |
| Expired claim/commit | Validator | - | -100 bps |

All updates are `internal` function calls. No cross-contract overhead.

## 7. Gas Comparison

| Operation | Current (estimated) | Redesign (estimated) | Delta |
|---|---|---|---|
| `computeConsensus` (3 validators) | ~300k (embedded in finalize, includes cross-contract calls to Oracle, Trust) | ~150k (library + internal calls) | -50% |
| Validator settlement (per validator) | ~100k (embedded in finalize loop, cross-contract slash + trust + rewards) | ~80k (one vault call + internal) | -20% |
| Total finalization (3 validators, accepted) | ~500k+ (one atomic tx) | ~150k + 3×80k + 50k = ~440k (spread across 5 txs) | Similar total, but no single tx exceeds 150k and each step is independently retriable |
| Reputation update | ~8k (external CALL + SLOAD + SSTORE) | ~5k (internal SLOAD + SSTORE) | -37% |
| Claim expiry + index reclamation | Two transactions + off-chain index tracking | One transaction, self-contained | Simpler, no liveness risk |

The total gas is comparable, but the distribution changes dramatically. No single transaction risks exceeding block gas limits or reverting partway through a complex multi-step operation.

## 10. Access Control

```solidity
// Roles
bytes32 constant DEFAULT_ADMIN_ROLE = 0x00;
bytes32 constant OPERATOR_ROLE = keccak256("OPERATOR_ROLE");

// All participant functions are permissionless (anyone with stake can participate).
// Admin functions:
//   - setProtocolFee(uint256 bps)
//   - setOriginationFee(uint256 bps)
//   - setContributionFee(uint256 bps)
//   - setValidationFee(uint256 bps)
//   - setDecayRate(uint256 bps)
//   - setConsensusAlgorithm(address)
//   - pause() / unpause()
//
// View functions (adapter fees):
//   - getAdapterFees() → (originationBps, contributionBps, validationBps)
//   - getOriginationAdapter(projectId) → address
//   - getContributionAdapter(claimId) → address
//   - getValidationAdapter(projectId, index, validator) → address
```

No `UPDATER_ROLE` needed because reputation updates are internal functions, not cross-contract calls requiring role-gated access.

**Smart Account constraints:**

- The protocol must **never** use `tx.origin`. With 4337, `tx.origin` is the Bundler, not the user. All authorization checks use `msg.sender` only.
- No `ecrecover` in protocol contracts. Signature validation happens in the Smart Account, not in QualityEngine or StakeVault.
- The commit hash verification (`keccak256(score, stakeAmount, salt)`) is data-level, not signature-level, and is unaffected.

**Server as keeper:**

The Sapien server holds the `OPERATOR_ROLE` and acts as the primary keeper for permissionless maintenance functions:

- `expireClaim(claimId)` — reclaim expired contribution slots
- `computeConsensus(projectId, index)` — trigger consensus after sufficient reveals
- `cancelExpiredValidationClaim(claimId)` — expire and slash idle validator claims
- `cancelExpiredCommitment(projectId, index, validator)` — expire and slash ghost validators

These functions remain permissionless (anyone can call them), but in practice the server is the primary caller and batches them via UserOperations.

**No contract-level batch functions:**

Batching is handled at the ERC-4337 UserOperation layer (see Section 3.5). The protocol contracts expose only single-item functions. This eliminates `MAX_BATCH_SIZE` limits and simplifies the contract surface.

## 11. Migration Path

If implementing incrementally against the existing codebase rather than a clean rewrite:

1. **Phase 0**: Deploy account abstraction infrastructure — Coinbase Smart Wallet factory, Paymaster contract, session key management. Verify all existing protocol functions work when called from Smart Accounts (no `tx.origin` issues). This phase is independent of the protocol refactor and can proceed in parallel.
2. **Phase A**: Merge `Rewards` into `SapienCore` (lowest risk, biggest simplification). Replace the external Rewards contract with internal escrow mappings.
3. **Phase B**: Merge `SapienTrust` into `SapienCore`. Replace cross-contract reputation calls with internal functions. Remove `UPDATER_ROLE`.
4. **Phase C**: Merge `ValidationOracle` into `SapienCore`. Eliminate duplicated project state. Switch validation storage from arrays to nonce-keyed mappings.
5. **Phase D**: Implement phased finalization (`computeConsensus` / `settleValidator` / `claimReward`). Remove contract-level batch functions (batching moves to UserOp layer).
6. **Phase E**: Implement claim-embedded indices. Replace stack + separate reclamation with atomic expiry.
7. **Phase F**: Refactor `StakeVault` to include `contributorLock` / `validatorCapacity` / `inFlight` categories.
8. **Phase G**: Configure session key scoping — define allowed selectors for server session key, enforce passkey-only for `commitValidation` and `revealValidation`. Deploy Paymaster with sponsorship policies.

Phase 0 and Phases A–F can proceed in parallel. Phase G is the final integration step that wires the account abstraction layer to the refactored protocol.

## 12. What Stays the Same

These mechanisms are well-designed and battle-tested through security reviews. They carry over unchanged:

- ERC-4626 vault with share-burn slashing
- Commit-reveal validation scheme
- sqrt(stake) consensus weighting
- Asymmetric reputation (hard to earn, easy to lose)
- Lazy reputation decay
- Daily reputation gain cap
- Tiered slashing by standard deviation (1.5σ–5σ)
- Challenge period before contributor reward release
- Reward rate snapshot at submission time (anti-sandwich)
- Minimum stake requirements per role
- Per-role, per-skill reputation tracking
- Nonce-based invalidation of stale validations on rejection/resubmission

## 13. Dispute Mechanism & Originator Accountability

### 13.1 Overview

The challenge period (1 day after consensus) is an active dispute window, not dead time. Any participant with vault stake can challenge a consensus outcome by posting a bond. Additionally, originators must post stake that can be slashed for misconduct (data unavailability, misleading specifications, project abandonment).

Two dispute surfaces exist:

1. **Consensus outcome disputes** — a user challenges whether a contribution was correctly accepted or rejected
2. **Originator misconduct reports** — a user reports the originator for bad faith behavior

Both use an optimistic pattern: outcomes stand unless challenged within a window, and the operator resolves disputes off-chain within a deadline. If the operator fails to act, disputes auto-escalate in the challenger's favor.

### 13.2 Data Model

```solidity
enum DisputeStatus { None, Open, Upheld, Rejected }
enum OriginatorReportStatus { None, Open, Upheld, Rejected }

struct Dispute {
    address challenger;
    uint256 bondAmount;
    uint64  openedAt;
    uint64  resolvedAt;
    DisputeStatus status;
    bytes32 evidenceHash;     // keccak256 of off-chain evidence (IPFS CID)
}

struct OriginatorReport {
    address reporter;
    uint256 bondAmount;
    uint64  reportedAt;
    uint64  resolvedAt;
    OriginatorReportStatus status;
    bytes32 evidenceHash;
}

// Storage (added to EngineStorage):
mapping(bytes32 => mapping(uint256 => Dispute)) disputes;
uint256 disputeBondBps;                              // default 1000 (10% of rewardRate)

mapping(bytes32 => uint256) originatorLockedStake;
mapping(bytes32 => OriginatorReport) originatorReports;
uint256 originatorStakeRequirement;                  // per-slot, default 0 (disabled)
uint256 originatorReportBondBps;                     // default 100 (1% of totalRewards)
```

### 13.3 Constants

| Constant | Value | Description |
|---|---|---|
| `DISPUTE_RESOLUTION_DEADLINE` | 7 days | Operator must resolve within this window or dispute auto-escalates |
| `MAX_DISPUTE_BOND_BPS` | 5000 | 50% cap on dispute bond |
| `DISPUTE_CHALLENGER_REWARD_BPS` | 2000 | 20% of saved/slashed amount goes to successful challenger |
| `MAX_ORIGINATOR_REPORT_BOND_BPS` | 1000 | 10% cap on originator report bond |

### 13.4 Consensus Disputes

#### Opening a Dispute

```
Challenger                          QualityEngine                   StakeVault
    |                                    |                              |
    +- openDispute(projectId,            |                              |
    |   index, evidenceHash) ----------->|                              |
    |                                    +- verify consensus computed   |
    |                                    +- verify within challenge     |
    |                                    |   period (challengeEndsAt)   |
    |                                    +- verify no active dispute    |
    |                                    +- verify challenger !=        |
    |                                    |   contributor (for accepted) |
    |                                    |                              |
    |                                    +- bond = rewardRate *         |
    |                                    |   disputeBondBps / BPS       |
    |                                    +- lockContributor(challenger, |
    |                                    |   bond) ------------------->|
    |                                    |                              |
    |                                    +- store Dispute               |
    |                                    +- extend challengeEndsAt      |
    |                                    |   (freeze reward release)    |
    |                                    +- emit DisputeOpened          |
```

Key constraints:
- Dispute must be filed during the challenge period (now set for both accepted and rejected contributions)
- Only one active dispute per contribution at a time
- The contributor cannot dispute their own acceptance (they would be disputing their own reward)
- Bond is locked from the challenger's vault stake

#### Resolving a Dispute

```
Operator                            QualityEngine                   StakeVault
    |                                    |                              |
    +- resolveDispute(projectId,         |                              |
    |   index, upheld) ---------------->|                              |
    |                                    +- verify dispute is Open      |
    |                                    +- verify OPERATOR_ROLE        |
    |                                    |                              |
    |                                    +- if upheld:                  |
    |                                    |   unlock challenger bond -->|
    |                                    |   // Compensation based on   |
    |                                    |   // original outcome:       |
    |                                    |   [see below]                |
    |                                    |                              |
    |                                    +- if rejected:                |
    |                                    |   slash challenger bond ---->|
    |                                    |   unfreeze reward release    |
    |                                    |                              |
    |                                    +- emit DisputeResolved        |
```

#### Dispute Outcomes

**Overturning an ACCEPTANCE (dispute says: "this was garbage"):**

| Action | Effect |
|---|---|
| Reward release | Permanently blocked (reward stays in escrow) |
| Challenger bond | Returned |
| Challenger reward | 20% of contribution's rewardRate from escrow |
| Contributor reputation | Penalty applied |
| Contributor stake | Already unlocked at consensus time (limitation of v1) |
| Validator settlements | Unaffected (already happened) |

**Overturning a REJECTION (dispute says: "this was quality work"):**

This uses a compensation-only approach. The original state changes (contributor stake slash, index return, nonce increment) cannot be reversed. Instead:

| Action | Effect |
|---|---|
| Contributor compensation | Full rewardRate paid from escrow |
| Challenger bond | Returned |
| Challenger reward | 20% of rewardRate from escrow |
| Contributor reputation | Positive update applied |
| Contributor burned shares | Not recoverable (known v1 limitation) |
| Index/nonce | Not reversed (index may have been reclaimed) |

#### Auto-Escalation

If the operator doesn't resolve a dispute within `DISPUTE_RESOLUTION_DEADLINE` (7 days), anyone can call `escalateDispute(projectId, index)` to auto-uphold the dispute. This prevents disputes from freezing funds indefinitely and removes an operator griefing vector.

### 13.5 Originator Accountability

#### Originator Stake

When `originatorStakeRequirement > 0`, the originator must hold vault shares (sSAPIEN). At `fundProject` time, `originatorStakeRequirement * quantity` is locked from the originator's vault balance via `lockContributor`. This stake is held for the project's lifetime and is slashable via originator reports.

#### Reporting Misconduct

```
Reporter                            QualityEngine                   StakeVault
    |                                    |                              |
    +- reportOriginator(projectId,       |                              |
    |   evidenceHash) ----------------->|                              |
    |                                    +- verify project Active/Funded|
    |                                    +- verify reporter != originator|
    |                                    +- verify no active report     |
    |                                    |                              |
    |                                    +- bond = totalRewards *       |
    |                                    |   originatorReportBondBps/BPS|
    |                                    +- lockContributor(reporter,   |
    |                                    |   bond) ------------------->|
    |                                    |                              |
    |                                    +- store OriginatorReport      |
    |                                    +- pause new claims            |
    |                                    |   (report blocks claiming)   |
    |                                    +- emit OriginatorReported     |
```

Misconduct scenarios:
- **Data unavailability** — validators/contributors can't access required data
- **Misleading specifications** — task description doesn't match actual requirements
- **Project abandonment** — originator funded but never follows through

#### Resolving a Report

```
Operator                            QualityEngine                   StakeVault
    |                                    |                              |
    +- resolveOriginatorReport(          |                              |
    |   projectId, upheld) ------------>|                              |
    |                                    |                              |
    |                                    +- if upheld:                  |
    |                                    |   unlock reporter bond ---->|
    |                                    |   slash originator stake --->|
    |                                    |   reporter reward from escrow|
    |                                    |   reputation penalty         |
    |                                    |   project.status = Cancelled |
    |                                    |                              |
    |                                    +- if rejected:                |
    |                                    |   slash reporter bond ------>|
    |                                    |   project resumes            |
    |                                    |                              |
    |                                    +- emit OriginatorReportResolved|
```

When a project is cancelled:
- No new claims allowed
- Existing in-flight contributions continue through their pipeline normally
- Active claims can be expired via existing `expireClaim` mechanism
- Remaining escrow is not automatically refunded (could be claimed by an admin function in a future version)

Auto-escalation works identically to consensus disputes: if the operator doesn't resolve within 7 days, `escalateOriginatorReport(projectId)` auto-upholds the report.

### 13.6 Session Key Additions

The following dispute functions should be added to the server session key's allowed selectors:

```
// Dispute functions (server session key OK — these are keeper/resolution duties)
resolveDispute(bytes32, uint256, bool)              // OPERATOR_ROLE
resolveOriginatorReport(bytes32, bool)              // OPERATOR_ROLE
```

The following must be **passkey-signed** (user-initiated disputes require user consent):

```
openDispute(bytes32, uint256, bytes32)              // PASSKEY — locks user's bond
reportOriginator(bytes32, bytes32)                  // PASSKEY — locks user's bond
escalateDispute(bytes32, uint256)                   // session key OK — permissionless keeper
escalateOriginatorReport(bytes32)                   // session key OK — permissionless keeper
```

### 13.7 Known Limitations (v1)

1. **Rejection overturns are compensation-only.** Contributor's burned vault shares cannot be restored. The contributor is made whole via reward token compensation, but their sSAPIEN position takes a permanent loss.

2. **Validator settlements are not reversed.** If a dispute overturns an acceptance, validators who already settled and received rewards keep them. The economic loss falls on the project escrow.

3. **Single dispute per contribution.** Only one active dispute at a time. A rejected dispute cannot be re-opened (the window has passed).

4. **Centralized resolution.** The operator (OPERATOR_ROLE) resolves disputes off-chain. Decentralized resolution (e.g., re-validation by a fresh validator set) is a v0.5 enhancement.

5. **Originator stake is optional.** The `originatorStakeRequirement` defaults to 0. Without originator stake, the originator report mechanism has limited economic teeth (only reputation penalty and project cancellation).

## 14. ERC-4337 Integration Details

### 14.1 Coinbase Smart Wallet

Each user is represented by a Coinbase Smart Wallet — an ERC-4337 compliant smart contract account.

- **Owner:** User's passkey (WebAuthn / FIDO2 credential). No seed phrase, no browser extension.
- **Session keys:** Delegated signing authority granted to the Sapien server. Scoped by function selector, bounded by time.
- **Recovery:** Coinbase recovery service + optional social recovery signers.
- **Deployment:** Deterministic CREATE2 from factory. Address is known before first transaction.

### 14.2 Session Key Scoping

The server's session key is authorized for specific function selectors on QualityEngine and StakeVault. The session key **must not** be authorized for `commitValidation` or `revealValidation` to preserve commit-reveal integrity.

**Server session key — allowed selectors:**

```
// QualityEngine
claimToContribute(bytes32, uint256, address)     // adapter param added
contribute(uint256, uint256, bytes32)
expireClaim(uint256)
releaseContributorReward(bytes32, uint256)
claimReward(address)
setValidatorCapacity(uint256)
claimToValidate(bytes32, address)                // adapter param added
settleValidator(bytes32, uint256)
computeConsensus(bytes32, uint256)
cancelExpiredValidationClaim(uint256)
cancelExpiredCommitment(bytes32, uint256, address)
escalateDispute(bytes32, uint256)                   // permissionless keeper
escalateOriginatorReport(bytes32)                   // permissionless keeper

// StakeVault
deposit(uint256, address)
withdraw(uint256, address, address)
```

Note: The server naturally passes its own adapter address (or the adapter address of the frontend it operates for) when calling `claimToContribute` and `claimToValidate` via session key. The `fundProject` call includes the adapter param but is typically called directly by the originator, not via the server session key.

**Passkey-only — NOT allowed via session key:**

```
commitValidation(bytes32, uint256, bytes32, uint128)
revealValidation(bytes32, uint256, uint16, bytes32)
openDispute(bytes32, uint256, bytes32)              // locks user's bond
reportOriginator(bytes32, bytes32)                  // locks user's bond
```

### 14.3 Paymaster

A Sapien-operated Verifying Paymaster sponsors gas for all protocol UserOperations. This means:

- Users never hold ETH for gas.
- The server controls sponsorship policy (rate limits, per-project budgets, abuse prevention).
- The Paymaster verifies that the UserOp targets QualityEngine or StakeVault before sponsoring.
- Paymaster costs are a protocol operational expense, offset by protocol fees.

### 14.4 Bundler

The Sapien server operates (or delegates to) an ERC-4337 Bundler that:

- Receives signed UserOps from users (for commit/reveal) and from the server (for delegated actions).
- Batches UserOps into single on-chain transactions where possible.
- Provides a standard `eth_sendUserOperation` JSON-RPC endpoint.

### 14.5 ERC-8004 Relationship

The `docs-v0.4/architecture/8004/` plan for full ERC-8004 identity integration is **deferred, not abandoned**. The Coinbase Smart Wallet approach covers:

- Stable on-chain identity (Smart Account address is permanent)
- Signer rotation (add/remove passkeys without changing address)
- Delegation (session keys)
- Recovery (Coinbase + social recovery)

The remaining ERC-8004 concerns — cross-chain identity portability, registry-level interoperability, identity-keyed analytics — can be addressed as an **off-chain middleware layer** that maps Smart Account addresses to ERC-8004 `(chainId, identityRegistry, agentId)` tuples. This avoids re-keying protocol state from `address` to `bytes32 agentKey`, saving ~13 new contracts and a full protocol rewrite.

If strict on-chain ERC-8004 compliance becomes a hard requirement in the future, it can be introduced as a registry adapter that the protocol reads during identity checks, without changing the core state model.
