## 3. Web App

### 3.1 Tech Stack

| Layer | Choice | Rationale |
|---|---|---|
| Build tool | Vite | Fast HMR, simple config, no SSR overhead — this is a client-rendered app behind auth |
| Routing | TanStack Router | Type-safe file-based routing, built-in search param validation, loader pattern for data fetching |
| Data fetching | TanStack Query | Cache management, background refetch, optimistic updates. Queries hit both the API Server and Ponder's GraphQL endpoint |
| Client state | Zustand | Lightweight store for ephemeral client state (salt storage, form wizard steps, UI preferences) |
| Wallet | Coinbase Smart Wallet SDK (`@coinbase/wallet-sdk`) | Native passkey support, session key management, ERC-4337 UserOp construction |
| Chain interaction | viem + wagmi | Type-safe contract reads/writes, hooks for React |
| Styling | Tailwind CSS + shadcn/ui | Rapid UI development, accessible components |
| Real-time | WebSocket client (native or socket.io-client) | Live progress updates, notification delivery |

### 3.2 Client-Side Responsibilities

The web app is not a thin shell — it owns critical logic that cannot be delegated to the server.

| Responsibility | Why Client-Side | Details |
|---|---|---|
| **Passkey management** | Security — private key never leaves device | Create wallet, sign commit/reveal UserOps |
| **Salt generation & storage** | Commit-reveal integrity — server must not see salt | Generate `crypto.getRandomValues()`, persist in IndexedDB + localStorage |
| **Commit hash computation** | Server must not see score | `keccak256(abi.encodePacked(score, stakeAmount, salt))` computed in browser |
| **UserOp signing (commit/reveal)** | Passkey-only operations | Client constructs full calldata, signs via WebAuthn, sends signed UserOp to server for relay |
| **Data validation (originator upload)** | Fail fast, reduce server load | JSON schema validation, file format checks, naming convention enforcement — all before upload |
| **Contribution work interface** | Task-type specific, adapter-defined | The actual "do the work" UI — could be a labeling tool, a text editor, an AI review interface |

### 3.3 Session Key Flow (Client Perspective)

```
1. User creates Coinbase Smart Wallet (passkey prompt)
2. App requests session key grant:
   - Scoped selectors: claimToContribute, contribute, expireClaim,
     releaseContributorReward, claimReward, setValidatorCapacity,
     claimToValidate, settleValidator, computeConsensus, deposit, withdraw
   - NOT included: commitValidation, revealValidation
   - Time bound: 30 days (renewable)
3. User confirms with passkey
4. Session key sent to API Server (encrypted, stored server-side)
5. For delegated actions: app calls API Server → server builds UserOp → signs with session key → sends to Bundler
6. For passkey actions: app builds UserOp locally → user signs with passkey → app sends signed UserOp to API Server → server relays to Bundler
```

### 3.4 Salt Persistence Strategy

The validator salt is the single most dangerous piece of client state. If lost before reveal, the validator forfeits their stake.

| Storage Layer | Purpose | Persistence |
|---|---|---|
| IndexedDB | Primary store — survives page refreshes, tab closes | Until explicitly deleted or browser data cleared |
| localStorage | Backup — faster reads for reveal-time lookup | Same as IndexedDB |
| Optional: encrypted cloud backup | User-initiated export to their own storage | User downloads encrypted JSON blob; can re-import on new device |

**Data shape per pending commit:**

## 4. API Server

### 4.1 Responsibilities

The API server is the central orchestrator. It bridges the web app, the blockchain, data storage, and notifications.

| Responsibility | Details |
|---|---|
| **UserOp construction & relay** | Build UserOps for delegated actions (session key), relay passkey-signed UserOps to Bundler |
| **Session key custody** | Store encrypted session keys per user, use them to sign UserOps on behalf of users |
| **Data upload handling** | Receive validated data files from originator, store to object storage, confirm counts |
| **Data serving** | Serve data points to contributors and validators (pre-signed URLs or proxied reads) |
| **Ponder proxy / app state API** | Proxy Ponder's GraphQL endpoint (indexed on-chain state) and expose REST endpoints for app-specific data (uploads, profiles, sessions) |
| **WebSocket gateway** | Push real-time state updates to connected clients (progress, consensus results, notifications) |
| **Authentication** | Verify Smart Account ownership via SIWE (Sign-In With Ethereum) or session tokens |

### 4.2 Tech Stack

| Layer | Choice | Rationale |
|---|---|---|
| Runtime | Node.js 22 | TypeScript ecosystem, viem compatibility |
| Framework | Hono or Fastify | Lightweight, fast, middleware-friendly |
| ORM | Drizzle | Type-safe, migration-friendly, Postgres-native — used for App DB only (Ponder manages its own DB) |
| UserOp SDK | Alchemy AA SDK (`@alchemy/aa-core`) or viem 4337 actions | Build, sign, and submit ERC-4337 UserOperations via Alchemy's bundler |
| Object Storage | AWS SDK v3 (`@aws-sdk/client-s3`) — Railway's S3-compatible bucket uses the same API | Pre-signed URLs, multipart uploads |
| WebSocket | Hono WebSocket adapter or ws | Real-time push to clients |
| Auth | SIWE (Sign-In With Ethereum) | User proves Smart Account ownership by signing a message with their passkey |
| Queue | BullMQ (Redis-backed) | Async job processing for keeper tasks, notifications |

### 4.3 Authentication: Smart Account Ownership

The server needs to verify that API callers own the Smart Account they claim. This uses SIWE:

```
1. Client requests nonce from server
2. Client constructs SIWE message with Smart Account address + nonce
3. Client signs message with passkey (via Coinbase Smart Wallet SDK)
4. Client sends signature + message to server
5. Server verifies signature via ERC-1271 isValidSignature() on the Smart Account contract
6. Server issues a JWT / session cookie bound to the Smart Account address
7. Subsequent API calls include the JWT — no re-signing needed until expiry
```

**Why ERC-1271, not ecrecover:** Smart Accounts don't have a private key — they validate signatures via their own contract logic (which checks the passkey/WebAuthn credential). The server calls `isValidSignature(hash, signature)` on the Smart Account to verify.

### 4.5 UserOp Construction & Relay

The server operates in two modes depending on the action:

**Mode 1: Delegated (session key)** — Server builds the full UserOp, signs it with the user's session key, and sends to the Bundler.

```
App                         API Server                      Bundler
 │                               │                              │
 ├─ POST /projects/:id/claim ──►│                              │
 │   { qty: 3 }                 │                              │
 │                               ├─ Build calldata:             │
 │                               │   claimToContribute(         │
 │                               │     projectId, 3, adapter)   │
 │                               │                              │
 │                               ├─ Build UserOp:               │
 │                               │   sender: user's SmartAcct   │
 │                               │   callData: above            │
 │                               │   paymaster: Sapien paymaster│
 │                               │                              │
 │                               ├─ Sign with session key       │
 │                               │                              │
 │                               ├─ eth_sendUserOperation ─────►│
 │                               │                              ├─ Bundle + submit
 │                               │◄─ userOpHash ───────────────┤
 │◄─ { userOpHash, status } ────┤                              │
```

**Mode 2: Relay (passkey-signed)** — Client builds and signs the full UserOp; server just forwards it.

```
App (browser)                API Server                     Bundler
 │                               │                              │
 ├─ Build calldata locally:      │                              │
 │   commitValidation(           │                              │
 │     projId, index,            │                              │
 │     commitHash, stakeAmt)     │                              │
 │                               │                              │
 ├─ Build full UserOp            │                              │
 ├─ Sign with passkey (WebAuthn) │                              │
 │                               │                              │
 ├─ POST /validations/commit ──►│                              │
 │   { signedUserOp }           │                              │
 │                               ├─ Validate envelope only     │
 │                               │   (sender matches authed    │
 │                               │    user, targets allowed    │
 │                               │    contract — does NOT      │
 │                               │    inspect calldata)        │
 │                               │                              │
 │                               ├─ eth_sendUserOperation ─────►│
 │                               │                              ├─ Bundle + submit
 │                               │◄─ userOpHash ───────────────┤
 │◄─ { userOpHash } ────────────┤                              │
```

**Schema registry:** The server maintains a registry of JSON schemas per task type. When a project is created with a specific task type, the schema is fixed. Both client and server validate against the same schema.

## 5. Indexer (Ponder)

### 5.1 Why Ponder

[Ponder](https://ponder.sh) is a framework purpose-built for blockchain indexing. It replaces a custom indexer process with a declarative configuration and handles the hard infrastructure problems automatically.

| Concern | Custom Indexer | Ponder |
|---|---|---|
| Reorg handling | Manual cursor tracking, rollback logic, idempotent writes | Built-in — Ponder tracks chain state and automatically rewinds on reorg |
| Schema management | Hand-written SQL migrations | Declarative `ponder.schema.ts` — Ponder generates tables and manages migrations |
| API layer | Custom REST endpoints or GraphQL server | Auto-generated GraphQL API from schema — zero boilerplate |
| Real-time | Custom Redis pub/sub + WebSocket wiring | Built-in live queries via GraphQL subscriptions |
| Hot reload | Restart process, replay from cursor | Instant hot reload in dev — schema and handler changes apply without full re-index |
| Type safety | Manual ABI parsing, hand-typed event args | Full end-to-end TypeScript types generated from ABIs and schema |

### 5.5 Event Handlers

Event handlers live in `src/` and map each on-chain event to database operations. Ponder provides the typed `event` object and a `context.db` handle for upserts.

**`src/QualityEngine.ts` (key handlers):**

```typescript
import { ponder } from "ponder:registry";
import * as schema from "ponder:schema";

ponder.on("QualityEngine:ProjectCreated", async ({ event, context }) => {
  await context.db.insert(schema.projects).values({
    id: event.args.projectId,
    originator: event.args.originator,
    // ... map all config params from event args
    status: "Created",
    availableSlots: 0,
    totalRewards: 0n,
    totalQuantity: 0,
    createdAt: event.block.timestamp,
  });
});

ponder.on("QualityEngine:ProjectFunded", async ({ event, context }) => {
  // Update project with funding data
  await context.db.update(schema.projects, { id: event.args.projectId }).set({
    totalRewards: event.args.amount,
    totalQuantity: Number(event.args.quantity),
    availableSlots: Number(event.args.quantity),
    status: "Active",
    fundedAt: event.block.timestamp,
  });

  // Create index rows: 0..quantity-1
  const qty = Number(event.args.quantity);
  for (let i = 0; i < qty; i++) {
    await context.db.insert(schema.indices).values({
      id: `${event.args.projectId}-${i}`,
      projectId: event.args.projectId,
      indexNum: i,
      status: "Available",
      nonce: 0,
    });
  }
});

ponder.on("QualityEngine:ClaimCreated", async ({ event, context }) => {
  await context.db.insert(schema.claims).values({
    id: event.args.claimId,
    projectId: event.args.projectId,
    claimant: event.args.claimant,
    totalCount: event.args.indices.length,
    submittedCount: 0,
    deadline: event.args.deadline,
    status: "Active",
    createdAt: event.block.timestamp,
  });

  // Mark each index as Reserved
  for (const idx of event.args.indices) {
    await context.db
      .update(schema.indices, { id: `${event.args.projectId}-${idx}` })
      .set({
        status: "Reserved",
        reservedBy: event.args.claimant,
        claimId: event.args.claimId,
      });
  }

  // Decrement available slots
  await context.db.update(schema.projects, { id: event.args.projectId }).set((row) => ({
    availableSlots: row.availableSlots - event.args.indices.length,
  }));
});

ponder.on("QualityEngine:ConsensusReached", async ({ event, context }) => {
  const status = event.args.status === 1 ? "Accepted" : "Rejected";

  await context.db.insert(schema.consensusReports).values({
    id: `${event.args.projectId}-${event.args.index}-${event.args.nonce}`,
    projectId: event.args.projectId,
    indexNum: Number(event.args.index),
    nonce: Number(event.args.nonce),
    weightedAverage: Number(event.args.weightedAverage),
    stdDeviation: Number(event.args.stdDeviation),
    resultStatus: status,
    computedAt: event.block.timestamp,
  });

  // Update contribution and index status
  await context.db
    .update(schema.contributions, { id: `${event.args.projectId}-${event.args.index}` })
    .set({ status });

  await context.db
    .update(schema.indices, { id: `${event.args.projectId}-${event.args.index}` })
    .set({ status });
});

// ... similar handlers for ContributionSubmitted, ValidationClaimed,
//     ValidationCommitted, ValidationRevealed, ValidatorSettled,
//     ClaimExpired, ContributorRewardReleased, RewardClaimed,
//     ReputationUpdated, OriginationFeePaid, ContributionAdapterFeePaid,
//     ValidationAdapterFeePaid
```

| On-Chain Event | Ponder Table(s) Updated | Key Fields Extracted |
|---|---|---|
| `ProjectCreated` | `projects` | projectId, originator, config params |
| `ProjectFunded` | `projects`, `indices` | amount, quantity; create index rows 0..qty-1 with status `Available` |
| `ClaimCreated` | `claims`, `indices`, `projects` | claimId, claimant, indices[], deadline; mark indices as `Reserved`, decrement slots |
| `ClaimExpired` | `claims`, `indices`, `projects` | Mark claim `Expired`; return unsubmitted indices to `Available`, increment slots |
| `ContributionSubmitted` | `contributions`, `indices`, `claims` | contributor, submissionHash; mark index `Submitted`, increment submittedCount |
| `ValidationClaimed` | `validations` | validator, projectId, index |
| `ValidationCommitted` | `validations` | Store commitHash and committedAt (no score visible — opaque hash) |
| `ValidationRevealed` | `validations` | Store score, stakeAmount, revealedAt |
| `ConsensusReached` | `consensusReports`, `contributions`, `indices` | weightedAverage, status (Accepted/Rejected); update index/contribution status |
| `ValidatorSettled` | `validations` | Mark settled, store outlier status |
| `ContributorRewardReleased` | `rewardsHistory`, `contributions` | contributor, amount; mark rewardReleased |

Ponder supports GraphQL live queries for real-time data. The web app subscribes to specific entities and receives updates as new blocks are processed.

### 5.9 Reorg Handling

Ponder handles chain reorganizations automatically. When a reorg is detected, Ponder:

1. Identifies the common ancestor block
2. Rolls back all database state created after that block
3. Replays event handlers from the fork point

No custom reorg logic is needed. This is one of the primary advantages of using Ponder over a custom indexer.

### 5.10 Ponder vs. App Database

The system uses two logical databases (can be separate Postgres instances or separate schemas in one instance):

| Database | Managed By | Contains | Access Pattern |
|---|---|---|---|
| **Ponder DB** | Ponder (auto-managed, do not write to directly) | All on-chain indexed state: projects, claims, indices, contributions, validations, consensus reports, reputation, rewards history, adapter fees | Read-only by API Server + Web App via GraphQL |
| **App DB** | API Server (Drizzle migrations) | User profiles, session metadata, notification preferences, S3 upload records (data_uploaded, data_count, data_hash), salt backup (encrypted), API auth tokens | Read/write by API Server |

The Ponder DB is the source of truth for on-chain state. The App DB stores off-chain application state that has no on-chain representation (uploads, preferences, sessions).

## 6. Keeper Service

### 6.1 Purpose

The keeper calls permissionless on-chain functions that no specific user is incentivized to call but that the protocol depends on for liveness.

### 6.2 Keeper Actions

| Action | Trigger | On-Chain Call | Frequency |
|---|---|---|---|
| **Expire claims** | Claim deadline has passed + status is still Active | `expireClaim(claimId)` | Poll every 30s, or trigger on block with deadline match |
| **Compute consensus** | `revealCount >= numberOfValidations` for a given `(projectId, index, nonce)` | `computeConsensus(projectId, index)` | Event-driven: trigger when `ValidationRevealed` event brings revealCount to threshold |
| **Settle validators** | Consensus computed + validator not yet settled | `settleValidator(projectId, index)` for each revealed validator | Event-driven: trigger after `ConsensusReached` |
| **Release contributor rewards** | Contribution accepted + challenge period elapsed | `releaseContributorReward(projectId, index)` | Poll every 60s for contributions past `challengeEndsAt` |
| **Cancel expired validation claims** | Validator claimed but never committed within window | `cancelExpiredValidationClaim(claimId)` | Poll every 60s |
| **Cancel expired commitments** | Validator committed but never revealed within window | `cancelExpiredCommitment(projectId, index, validator)` | Poll every 60s |

### 6.3 Architecture

```
┌──────────────────────────────────────────────┐
│               Keeper Service                  │
│                                               │
│  ┌──────────┐   ┌──────────┐   ┌──────────┐ │
│  │ Deadline  │   │ Consensus│   │ Reward   │ │
│  │ Watcher   │   │ Trigger  │   │ Releaser │ │
│  └─────┬────┘   └─────┬────┘   └─────┬────┘ │
│        │              │              │        │
│        └──────────────┼──────────────┘        │
│                       │                       │
│                ┌──────▼──────┐                │
│                │  Job Queue  │                │
│                │  (BullMQ)   │                │
│                └──────┬──────┘                │
│                       │                       │
│                ┌──────▼──────┐                │
│                │  UserOp     │                │
│                │  Builder    │                │
│                │  (operator) │                │
│                └──────┬──────┘                │
│                       │                       │
└───────────────────────┼───────────────────────┘
                        │
                   ┌────▼─────┐
                   │  Bundler │
                   └──────────┘
```

The keeper submits UserOps from the **operator account** (a dedicated Smart Account with `OPERATOR_ROLE`). These are permissionless calls — anyone could submit them — but the keeper ensures protocol liveness.

### 6.4 Batching Strategy

The keeper batches multiple actions into single UserOps where possible:

```
// Single UserOp: batch expire multiple claims
[
  qualityEngine.expireClaim(claimId_1),
  qualityEngine.expireClaim(claimId_2),
  qualityEngine.expireClaim(claimId_3),
]

// Single UserOp: compute consensus + settle all validators for an index
[
  qualityEngine.computeConsensus(projA, index1),
  qualityEngine.settleValidator(projA, index1),  // for validator A
  qualityEngine.settleValidator(projA, index1),  // for validator B
  qualityEngine.settleValidator(projA, index1),  // for validator C
]
```

### 6.5 Failure & Retry

| Scenario | Handling |
|---|---|
| UserOp reverts on-chain | Log error, mark job as failed, retry with exponential backoff (max 3 retries) |
| Bundler rejects UserOp | Check gas estimation, re-estimate, retry |
| Duplicate call (already computed/settled) | Idempotent on-chain — reverts with `ConsensusAlreadyComputed` or `AlreadySettled`. Catch and skip. |
| Keeper is down | On restart, query Ponder GraphQL for all actionable states (expired claims, ready consensus, unreleased rewards) and process them. No state is lost — the blockchain is the source of truth. |

### 8.2 Paymaster

The Sapien Paymaster is a **Verifying Paymaster** that signs a gas sponsorship approval for each UserOp.

**Off-chain signer flow:**

```
1. UserOp arrives at Paymaster service (from API Server or Bundler)
2. Paymaster service checks:
   a. Target contract is QualityEngine or StakeVault (whitelist)
   b. Caller's Smart Account is not rate-limited
   c. Gas estimate is within acceptable bounds
   d. Monthly sponsorship budget for this user not exceeded
3. Paymaster service signs the paymaster data
4. Signed paymaster data is included in the UserOp
5. On-chain, the Paymaster contract verifies the signature and pays gas
```

**Abuse prevention:**

| Policy | Limit | Rationale |
|---|---|---|
| Per-user daily gas budget | 0.01 ETH equivalent | Prevents a single user from draining the paymaster |
| Per-project gas budget | Proportional to project escrow | Larger projects justify more gas sponsorship |
| Function selector whitelist | Only QualityEngine + StakeVault functions | Prevents using the paymaster for unrelated transactions |
| Rate limiting | Max 100 UserOps per user per hour | Prevents scripted abuse |

**Reveal window notifications cannot be disabled.** They are critical to protocol integrity — missed reveals cause stake forfeiture. The UI should explain why.

## 11. Security Considerations

### 11.1 Server Trust Boundary

The server is a trusted operator but is **not trusted with validator scores**. The trust boundary:

| Server CAN | Server CANNOT |
|---|---|
| Submit delegated UserOps (claim, contribute, settle, reward) | See validator scores before reveal (calldata is opaque) |
| Store session keys (encrypted at rest) | Sign commit/reveal UserOps (passkey required) |
| Read all on-chain state (public) | Modify on-chain state without valid UserOp |
| Serve data files to authorized users | Access data files for projects the user isn't part of |
| Trigger keeper actions (permissionless functions) | Bypass session key scoping (enforced by Smart Account) |

### 11.2 Session Key Security

| Threat | Mitigation |
|---|---|
| Session key leaked | Time-bounded (30 days), function-scoped (cannot commit/reveal), user can revoke at any time from Smart Account |
| Server compromised | Attacker can claim/contribute/settle on behalf of users but cannot steal funds (rewards go to user's pendingRewards, not attacker) and cannot affect validator integrity (commit/reveal require passkey) |
| Session key expired | App detects 4337 revert on expired session key, prompts user to re-grant |

### 11.3 Data Integrity

| Concern | Solution |
|---|---|
| Originator uploads malformed data | Client-side validation + server-side re-validation before confirming upload |
| Data tampered after upload | API Server rejects writes to funded projects. Content hash stored in App DB at upload confirmation time. On-chain `projectId` + quantity provide a cross-check. |
| Contributor submits fake work | On-chain `submissionHash` = keccak256 of submission JSON. Validators can verify the off-chain submission matches the on-chain hash. |
| Object storage downtime | Railway object storage provides high durability. For reads, API Server can cache hot data points in Redis. |

### 11.4 Rate Limiting

| Endpoint | Limit | Scope |
|---|---|---|
| `POST /auth/*` | 10/min | Per IP |
| `POST /projects/:id/upload/*` | 100/min | Per user |
| `POST /projects/:id/claim` | 20/min | Per user |
| `POST /validations/commit` | 30/min | Per user |
| `GET /*` (reads) | 300/min | Per user |
| WebSocket connections | 5 concurrent | Per user |

## 13. Repository Structure

All off-chain code lives in a single Turborepo monorepo. The Solidity contracts repo (`sapien-contracts`) remains separate.

### 13.1 Why Monorepo

| Concern | Monorepo Advantage |
|---|---|
| **Shared ABIs** | Contract ABIs are generated from Foundry output and consumed by the web app (wagmi), API server (viem), and Ponder (indexer config). One source of truth, no npm publishing or copy-paste. |
| **Shared types** | TypeScript types for projects, claims, contributions, validations, etc. are derived from Solidity structs and used across all three apps. No type drift. |
| **Shared config** | Contract addresses, chain IDs, fee constants, reputation parameters — consumed by multiple apps from a single package. |
| **Shared validation schemas** | JSON schemas for data point validation run in both the web app (client-side) and API server (server-side). Same code, same schemas. |
| **Atomic changes** | When a contract ABI changes, you update the shared package and fix all consumers in a single PR. No cross-repo version coordination. |

### 13.2 Tooling

| Tool | Purpose |
|---|---|
| **Turborepo** | Task orchestration (`build`, `dev`, `lint`, `typecheck`), dependency graph resolution, remote caching |
| **pnpm** | Package manager with workspace support. Turborepo runs on top of pnpm workspaces. |
| **TypeScript** | All packages and apps. Shared base `tsconfig` in `tooling/typescript/`. |

### 13.7 Deployment (Railway)

Each app deploys independently via GitHub Actions triggered on merge to `main`:

| App | Railway Service Type | Build Command | Trigger |
|---|---|---|---|
| `apps/web` | Static site | `turbo run build --filter=web` | Changes in `apps/web/` or `packages/` |
| `apps/server` | Web service (Dockerfile) | Multi-stage Docker build from monorepo root | Changes in `apps/server/` or `packages/` |
| `apps/indexer` | Web service (Dockerfile) | Multi-stage Docker build from monorepo root | Changes in `apps/indexer/` or `packages/` |
| `apps/docs` | Static site | `turbo run build --filter=docs` | Changes in `apps/docs/` or `packages/` |

Turborepo's `--filter` flag ensures only the affected app and its transitive dependencies are rebuilt. Changes to `packages/contracts` trigger all three apps; changes to `apps/web` only trigger the web deploy.

### 13.8 Relationship to `sapien-contracts`

The Foundry/Solidity repo (`sapien-contracts`) remains a separate repository:

| Concern | Why Separate |
|---|---|
| Different toolchain | Foundry (Solidity) vs. Node.js (TypeScript) |
| Different CI | `forge test` vs. `turbo build` |
| Different change cadence | Contracts change less frequently, go through audits |
| Different artifact type | Deployed bytecode vs. runtime applications |

The bridge between repos is `packages/contracts`. A sync script reads Foundry's `out/*.json` build artifacts and generates the TypeScript ABI exports:

```bash
# Run from the monorepo root after building contracts
pnpm sync-abis --foundry-out ../sapien-contracts/out
```

This generates `packages/contracts/abis/QualityEngine.ts` and `packages/contracts/abis/StakeVault.ts` with typed ABI constants. The generated files are committed to the monorepo — no runtime dependency on the contracts repo.
