# SapienVault — Repo Audit & Improvement Plan

> **Scope note:** analysis only, no code modified. I read 100% of `src/` (421 nSLOC), all scripts, configs, docs, and the test/invariant/Halmos suites' structure. I did not execute `forge build`/`forge test` (read-only audit), so claims about test behavior are from reading, not running. The three audit PDFs in `audits/` were not re-read; I relied on the extracted findings doc. The teamshared memory tools are unavailable in Ask mode, so no recall/session logging was performed this turn.

---

## Executive Summary

**Overall health: A−.** This is a small (421 nSLOC core), production-deployed, thrice-audited ERC-4626 staking vault with an unusually strong verification culture: per-finding regression tests for every Quantstamp item, a Foundry invariant suite with ghost accounting, a Halmos formal-verification suite with honestly documented solver limits, and NatSpec that cross-references audit findings. The contract code itself is clean, bounded, and conservative; I found **no Critical or High on-chain findings**.

The top three **risks** are operational, not in the Solidity:

1. The pending V1→V2 mainnet upgrade is rehearsed only against a hand-reconstructed `SapienVaultV1` mock, never against the live proxy's real state on a fork.
2. CI enforces only fmt/build/test — none of the repo's own lint, coverage, static-analysis, or Halmos tooling gates anything.
3. Engine liveness is a documented single point of failure with no on-chain escape hatch for locked stake.

The top three **opportunities** are cheap: a mainnet-fork upgrade rehearsal test, a hardened CI pipeline (lint + slither/aderyn + coverage + a `[profile.ci]`), and a handful of doc/error-hygiene fixes.

**Calibration:** this project is at the "live funds on mainnet" maturity level, so safety-net work around the upgrade is the only thing I'd call urgent.

## Phase 1 — Repo Map

**Purpose.** Economic-security layer for Sapien's off-chain Proof-of-Quality network: a custodial ERC-4626 vault (`vSAPIEN`) over the SAPIEN token with opt-in stake locking, engine-controlled unlock/slash (share-burn with dilution compensation), pause, and a per-tranche minimum-deposit-age MEV guard. Deployed on Base mainnet and Base Sepolia (addresses in `README.md:5-8`).

**Stack.** Solidity 0.8.30, Foundry (via-IR, optimizer 200 runs), OpenZeppelin 5.5.0 + upgradeable (pinned via `foundry.lock` + git submodules), UUPS/ERC-1967 proxy, ERC-7201 namespaced storage. Verification: Forge unit/fuzz/invariant + Halmos. CI: one GitHub Actions workflow.

**Architecture sketch.** Single-contract design: `SapienVault` (632 lines) inherits `ERC4626Upgradeable` + `AccessControlDefaultAdminRulesUpgradeable` + `Pausable` + `ReentrancyGuard` + `UUPS`, implementing `ISapienVault`. All custom state lives in one ERC-7201 struct (`src/Types.sol:15-34`). Control flow: every share movement funnels through the `_update` override (`src/SapienVault.sol:463-515`), which routes mints into immature tranches, burns through mature-then-immature FIFO spill, and gates transfers on matured-unlocked balance. Two roles: `DEFAULT_ADMIN_ROLE` (admin/upgrade) and `ENGINE_ROLE` (unlock/slash, held by an off-chain server).

| Path | What it is |
|------|------------|
| `src/` | `SapienVault.sol`, `Types.sol` (namespaced storage), `interfaces/ISapienVault.sol` |
| `test/` | 1,886-line unit/fuzz suite, invariant handler + 7 invariants, V1→V2 migration tests |
| `test/audits/` | One regression-test file per Quantstamp finding (SAP-1…7, S1–S3) + extracted findings doc |
| `test/halmos/` | 8 Halmos symbolic suites; limits documented in `halmos.toml` |
| `script/` | Deploy scripts (3 variants) + `UpgradeVault.s.sol` with calldata/execute/verify modes + runbook |
| `audits/` | Three external audit PDFs (Quantstamp ×2, Zokyo) |
| `docs/SapienVault.md` | 232-line design doc incl. integrator checklist and operational considerations |
| `deployments/` | JSON address records per network |

**Surprises.** *(Pleasant)* The audit-findings-as-executable-tests pattern in `test/audits/` and the candid Halmos-limits documentation in `halmos.toml` are rare even in professional codebases. *(Less pleasant)* The CI workflow is a near-stock Foundry template that ignores the rest of the repo's tooling, and current branch `QS_Audit_June_2026` implies mainnet still runs V1 while this V2 code awaits an upgrade — making the upgrade path the highest-stakes artifact in the repo.

## Phase 2 — Audit Report

### Architecture & design — healthy

One cohesive contract with one storage struct, every balance mutation through a single choke point (`_update`), bounded loops (`MAX_IMMATURE_TRANCHES = 32`, `src/SapienVault.sol:60`), append-only storage evolution. Nothing to fix at this size.

### Security

**SEC-1 · Medium (judgment) — Mainnet upgrade rehearsed only against a reconstructed mock, never against live state.** The migration suite upgrades a locally deployed `SapienVaultV1` mock:

```solidity
// SapienVaultV1.sol, lines 19-22
/// @notice Frozen pre-SAP-1 implementation used ONLY by migration tests to
///         reproduce the legacy global-timer storage state (it writes
///         `lastDepositTimestamp`). It shares the ERC-7201 storage slot and the
///         first three struct fields with the production contract, so an
```

No test forks Base mainnet and runs `upgradeToAndCall(newImpl, initializeV2(admin))` against the real proxy at `0x60Bf…` with real depositor storage. The lazy migration (`_lazyMigrate`, `src/SapienVault.sol:151-163`) and the `AccessControlDefaultAdminRules` seeding in `initializeV2` (`src/SapienVault.sol:121-137`) both depend on assumptions about the deployed V1's storage that the mock encodes by hand. If any assumption is off (e.g. the live V1 wrote a slot the mock doesn't), the failure surfaces only after an irreversible mainnet upgrade on a contract holding user funds. The `[rpc_endpoints]` config already exists (`foundry.toml:31-34`); only the fork test is missing. **Why it matters:** this is the single highest-blast-radius action the team will take with this code.

**SEC-2 · Low (fact) — `initializeV2` reverts with a misleading `ZeroAddress()` when the supplied admin doesn't hold the role.**

```solidity
// SapienVault.sol, lines 121-122
    function initializeV2(address currentAdmin_) external reinitializer(2) {
        if (!hasRole(DEFAULT_ADMIN_ROLE, currentAdmin_)) revert ZeroAddress();
```

A failed Safe-executed upgrade tx would decode as "zero address" when the actual problem is "wrong admin supplied," costing diagnosis time during the most stressful operation. *(Note: fixing requires a new error in the ABI — trivially safe, but must land before the upgrade is executed.)*

**SEC-3 · Low (fact) — Two overlapping mainnet deploy scripts, one with hardcoded keys-of-power.** `script/DeployBaseMainnet.s.sol:14-15` hardcodes token and admin (`0x5602…`) and writes `deployments/base-mainnet.json`, while `script/DeployBase.s.sol:13-14` is env-driven for the same network. Running the stale one with an outdated hardcoded admin would deploy a vault governed by the wrong key. Since the vault is already deployed, these are now mostly footguns to delete or archive.

**Otherwise healthy (verified):** no secrets in the repo (`rg` over non-lib files found only documented env-var names); role gating on every privileged path; reentrancy surface limited to `rescueETH`, which is `nonReentrant` and CEI-ordered (`src/SapienVault.sol:618-625`); inflation attack mitigated by `_decimalsOffset() = 3` plus tests (`test_donationAttack_firstDepositor`, `test/SapienVault.t.sol:611`); the SAP-2 slash formula's denominator-positivity argument (`src/SapienVault.sol:543-545`) is correct given the virtual-share offset; `uint128` tranche casts (`src/SapienVault.sol:160,221,224`) are SafeCast-checked and unreachable at realistic SAPIEN supply (~3.4×10¹⁷ tokens-worth of shares at offset 3).

### Testing

**TEST-1 · Medium (judgment) — Invariant suite silently tolerates unexpected reverts.** `fail_on_revert = false` (`foundry.toml:15`) combined with blanket `try`/`catch` in the handler (`test/SapienVaultHandler.t.sol:113,125`) means a regression that makes `transfer` or `lockStake` revert in a state it shouldn't would not fail the suite — it would just silently shrink the explored state space. The handler is already careful enough (bounds via `maxWithdraw`/`maxRedeem`/`availableBalance`) that most paths could run with `fail_on_revert = true` after making the remaining calls revert-safe (e.g. skip `unlockStake`/`slashStake` while paused, `test/SapienVaultHandler.t.sol:131-155`).

**TEST-2 · Low (fact) — Invariant runs never vary admin parameters.** `minDepositAge` is pinned to 7 days at setup (`test/SapienVaultInvariant.t.sol:31`) and the handler has no actions for `setMinDepositAge`/`setMinTrancheSize`, so invariants are never checked across the `minAge = 0 ↔ nonzero` transition — precisely the transition where `_pushImmature` switches code paths (`src/SapienVault.sol:211-215`) and `_matureSharesView` changes semantics. The tranche-cap coalescing path is covered (`test/audits/SAP1_SharesTransferGriefing.t.sol:96`).

**TEST-3 · Low (can't fully verify) — Coverage is not measured anywhere automated.** `make coverage` exists (`Makefile:4`) but nothing records or gates it. Given the suite's breadth (≈110 unit/fuzz tests + 7 invariants + 8 Halmos files), coverage is probably high, but I could not verify without running it.

Strengths here are exceptional — see [Strengths](#strengths-preserve-these) below.

### DevEx & operations

**OPS-1 · Medium (fact) — CI enforces a fraction of the repo's own toolchain.** `.github/workflows/test.yml` runs only `forge fmt --check`, `forge build --sizes`, `forge test -vvv`. Not gated: `forge lint` (exists as `Makefile:3`), solhint (`.solhint.json` exists but is referenced by nothing), coverage, Aderyn/Slither (run manually — `report.md` is a locally generated Aderyn artifact), and Halmos. The repo's security posture lives in human discipline (the `agent-security-review` skill) instead of CI. **Why it matters:** a future contributor can merge code that fails every standard this repo demonstrably holds itself to.

**OPS-2 · Low (fact) — CI sets `FOUNDRY_PROFILE: ci` (`test.yml:9`) but `foundry.toml` defines no `[profile.ci]`,** so CI silently falls back to the default profile: via-IR builds plus the full invariant load (`runs = 1024`, `depth = 50`, `foundry.toml:13-14`) on every push of every branch. That is both slow and a misleading config — the knob looks wired but is connected to nothing.

### Documentation

**DOC-1 · Low (fact) — Findings doc contradicts the code it documents.** `test/audits/QS_SapienVault_Initial_Report_Findings.md:50` says "The `_deposit` override was removed," but a `_deposit` override exists (re-added for `minTrancheSize`):

```solidity
// SapienVault.sol, lines 196-202
    function _deposit(address caller, address receiver, uint256 assets, uint256 shares) internal override {
        SapienVaultStorage storage $ = _getSapienVaultStorage();
        if ($.minDepositAge > 0 && $.minTrancheSize > 0 && assets < $.minTrancheSize) {
            revert BelowMinTrancheSize(assets, $.minTrancheSize);
        }
        super._deposit(caller, receiver, assets, shares);
    }
```

**DOC-2 · Low (fact) — Stale comment in `verifyStorageLocation`:** the derivation comment at `src/SapienVault.sol:74` references `"sapien.storage.SapienCore"` while the actual namespace (line 76) is `"sapien.storage.SapienVault"`. Cosmetic, but in exactly the function whose job is storage-slot trust.

**DOC-3 · Low (fact) — No LICENSE file despite MIT SPDX headers throughout** (verified via file search: zero matches for `LICENSE*`). For a public repo backing a live protocol, the license grant is currently ambiguous.

### Code quality, performance, dependencies — healthy

**Code quality:** no duplication (S3 consolidated the mature-minus-locked math into `_availableMatureShares`, `src/SapienVault.sol:318-323`), no dead code found, the longest function (`_update`, 52 lines) is the justified choke point. One stylistic note *(fact)*: every event indexes its `uint256` amount (`src/interfaces/ISapienVault.sol:33-67`), which moves values into topics and leaves data empty — unconventional for indexers, but already ABI-frozen on mainnet; do not change it, document it. **Performance:** all loops bounded by the 32-tranche cap; gas griefing explicitly designed around. **Dependencies:** only forge-std v1.11.0 and OZ v5.5.0, pinned by tag+rev in `foundry.lock` — exemplary hygiene; no known CVEs against OZ 5.5.0 that touch the inherited modules (not exhaustively verified offline).

### Strengths (preserve these)

- **Audit findings as executable regression tests** (`test/audits/` — one file per finding over a shared `AuditBase.t.sol` fixture) with a status-tracked extraction doc. This is the best audit-traceability pattern I've seen in a repo this size.
- **Honest formal-verification posture:** Halmos suite plus documented solver limits and explicit mitigations (`halmos.toml:8-14`), instead of pretending symbolic coverage is complete.
- **Single-choke-point design:** all share movement through `_update`, making the security argument auditable in one place.
- **Disciplined upgrade engineering:** ERC-7201 append-only storage, lazy per-user migration, `reinitializer(2)` that can only bless the incumbent admin, and a three-mode upgrade script with post-upgrade assertions (`script/UpgradeVault.s.sol:82-99`).
- **Documentation that states uncomfortable truths** — engine liveness as a trust assumption, pooled-adapter socialized slashing, slippage guidance (`docs/SapienVault.md:199-223`).
- **Dependency pinning** via `foundry.lock` tag+rev.

### The ugly parts needing utmost priority

There is no smoking gun in the Solidity. The genuinely uncomfortable items are: the **unrehearsed live upgrade (SEC-1)** — everything else in this repo is belt-and-suspenders except the single most dangerous operation; **CI that doesn't enforce the repo's own standards (OPS-1/OPS-2)**; and the **misleading `ZeroAddress` revert sitting directly on the upgrade path (SEC-2)**, which must be fixed before the upgrade ships or not at all.

## Phase 3 — Improvement Strategy

**Theme 1: The upgrade is the product right now — rehearse it against reality.** Target state: the exact `upgradeToAndCall` calldata destined for the Safe is executed in a Base-mainnet fork test against the live proxy, with post-upgrade assertions over real depositor accounts (balances, ages, locked amounts, `defaultAdmin()`), and this runs in CI until the upgrade is executed. *Principle: test the artifact you ship, not a reconstruction of it.*

**Theme 2: Move the verification culture from human discipline into CI.** Target state: CI fails on `forge fmt`, `forge lint`, build, tests, and a static-analysis pass (Aderyn and/or Slither with a triaged baseline); coverage is reported on every PR; a defined `[profile.ci]` makes PR runs fast and a scheduled job runs the deep invariant + Halmos load nightly. *Principle: a repo's standards are whatever its CI enforces; everything else is aspiration.*

**Theme 3: Make the fuzzing adversarial about reverts and parameters.** Target state: the invariant handler is revert-safe and runs with `fail_on_revert = true`; admin parameters (`minDepositAge`, `minTrancheSize`, pause) are fuzzed as actions. *Principle: an invariant suite that ignores reverts can only find accounting bugs, not liveness bugs.*

**Theme 4: Pre-upgrade hygiene window.** Target state: the small ABI-touching and doc fixes (SEC-2 error, DOC-1/DOC-2 comments, script cleanup, LICENSE) land in the same release as the upgrade, because after it ships the implementation is live and the cost of every change rises. *Principle: batch irreversibility.*

**Explicitly NOT recommending:**

- **No redesign of engine-dependent unlock** (e.g. time-based forced exit). It's a deliberate, documented product/trust decision (`docs/SapienVault.md:212-219`) with regulatory context per the project's history; changing it is a product call, not an audit remediation. → Open Questions.
- **No change to the indexed-amount events** — ABI is live on mainnet; the cost to indexers of changing exceeds the cosmetic win.
- **No splitting of `SapienVault.sol`** — 632 lines with one storage struct is the right size; extraction would add proxy/storage risk for zero payoff.
- **No SAP-4 "deep redesign"** (share value decoupled from `totalAssets`) — Quantstamp itself scoped it out; effort is XL, the mitigation is sound.

**Definition of done (measurable):** (1) a fork-upgrade test passes in CI against live mainnet state; (2) CI fails on lint/static-analysis/coverage-regression; (3) invariant suite green with `fail_on_revert = true`; (4) zero contradictions between `docs/` + findings-doc and `src/` on re-review; (5) PR CI wall-time under ~10 min with the deep suite on a nightly schedule.

### Implementation sketches — top 3

**T1 — Fork upgrade rehearsal.** Add a `test/fork/` suite gated on `vm.envOr("BASE_MAINNET_RPC_URL", "")` being set (skip otherwise, so local runs don't break). Steps: `vm.createSelectFork(rpc)`; read the live admin via the proxy's `getRoleMember`/known Safe address; `vm.prank(safe)` → `proxy.upgradeToAndCall(address(new SapienVault()), abi.encodeCall(SapienVault.initializeV2, (safe)))`; then assert exactly what `_verify` in `script/UpgradeVault.s.sol:82-99` asserts, plus pick several real holder addresses (from `deployments/`/an indexer) and assert `maturedShares + pendingShares == balanceOf`, locked amounts preserved, and that a withdraw by an aged holder succeeds. *Gotchas:* pin the fork block for determinism; the live V1 has no `maturedShares()` — only call V2 views after the upgrade; CI needs the RPC URL as a secret and the job should be `continue-on-error: false` but isolated from unit tests so RPC flakiness doesn't block unrelated PRs.

**T6 — CI gates.** Split the workflow into jobs: fmt+lint (`forge fmt --check`, `forge lint src/`), build+test (PR profile), static (install Aderyn, run with `--output report-ci.md`, diff against a committed baseline or use its exit-code-on-new-findings mode; same idea for Slither with `--triage-database`), coverage (`forge coverage --ir-minimum --report lcov` + upload). *Gotchas:* Slither + via-IR sometimes needs `--compile-force-framework foundry` and the existing remappings; baseline the current 5 Aderyn Lows (`report.md`) rather than fixing the unfixable (centralization "risk" is the design).

**T3 — `initializeV2` error.** Add `error NotCurrentAdmin(address account);` to `ISapienVault`, replace the `ZeroAddress` revert at `src/SapienVault.sol:122`, update `test/SapienVaultMigration.t.sol` and the errors table in `docs/SapienVault.md:168`. *Gotcha:* this changes the implementation bytecode — it must be in the implementation that the Safe calldata points at, i.e. land it before generating the final upgrade calldata, then re-run T1.

## Open Questions

1. **Has the V1→V2 upgrade already been executed on Base mainnet or Sepolia?** The branch name and scripts suggest it's pending. Milestone 0/1 sequencing depends entirely on this.
2. **Should `minTrancheSize` be seeded at upgrade time?** It defaults to 0 (disabled) and `initializeV2` doesn't set it (`src/SapienVault.sol:121-137`), so dust-deposit griefing of a victim's newest tranche remains possible (bounded, by design). Is "admin sets it post-upgrade" the intended operational plan, and what's the production value?
3. **Engine-liveness escape hatch:** is the product/legal position settled that locked stake with a dead engine stays locked (admin pause/revoke can't unlock, `docs/SapienVault.md:212-219`)? If a future escape hatch is even on the table, deciding before more integrators build on the current semantics is much cheaper.
4. **Intended license:** SPDX says MIT — confirm before adding the LICENSE file (T9).
5. **CI budget:** is there an RPC provider + secrets policy for fork tests in GitHub Actions (T1), and an acceptable nightly-job duration for the full invariant + Halmos load (T2)?
