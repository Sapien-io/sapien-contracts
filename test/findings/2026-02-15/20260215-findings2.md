## Executive Summary

The Sapien PoQ v0.5 protocol implements a decentralized quality oracle for AI workflows using stake-weighted, consensus-based verification. The architecture consolidates five prior contracts into two (QualityEngine + StakeVault) with a consensus library, deployed behind UUPS proxies with ERC-7201 namespaced storage.

**Gate Status: FAIL — 2 release blockers identified.**

The protocol demonstrates strong defensive engineering in many areas: fee-on-transfer token handling (M-02), ERC-4626 inflation attack mitigation, checks-effects-interactions pattern, SafeERC20 usage, and well-structured access control. However, a critical gap in the validator settlement path causes permanent fund loss on every contribution rejection — a routine protocol operation.

## High Severity Findings

### H-01: Validator In-Flight Stake Permanently Locked on Contribution Rejection
**ID:** SEC-SETTLE-001 | **Likelihood:** HIGH | **Release Blocker**

When `computeConsensus` determines that a contribution's weighted average falls below the project's consensus threshold, the contribution is marked as `Rejected` and `report.computed` intentionally stays `false` (to allow recomputation after resubmission at the same index).

However, `settleValidator` — the only function that releases or slashes validator in-flight stake — gates on `if (!report.computed) revert`. This means validators who participated in the rejected consensus round have no path to recover their committed stake:

- `settleValidator` reverts because `!report.computed`
- `cancelExpiredCommitment` reverts because the validator DID reveal (`revealedAt != 0`)
- No other function calls `vault.releaseCommit` or `vault.slashValidator`

The `validatorConsensus` mapping is keyed by `(projectId, index, validator)` — not by nonce — so results are overwritten if the index is resubmitted. Even if the settlement gate were removed, old validators' consensus data would be lost.

**Impact:** Every rejection permanently locks `stakeAmount` per participating validator. With 3 validators at 100 tokens each, 300 tokens are lost per rejection. Validators would quickly discover this and exit the system.

**Evidence:**
- `QualityEngine.sol:704-728` — Rejection path keeps `report.computed = false`
- `QualityEngine.sol:741-742` — `settleValidator` gates on `report.computed`

**Fix:** Add a dedicated `settleValidatorOnRejection` function or introduce a `report.finalized` flag that is set for both outcomes. See `fix_plan.md` for implementation details.

---

### H-02: Escrow Underflow in settleValidator After Dispute Deductions
**ID:** SEC-ESCROW-002 | **Likelihood:** MEDIUM | **Release Blocker**

The `settleValidator` function deducts validator rewards from `projectEscrow` without an underflow guard:

```solidity
$.projectEscrow[projectId][proj.rewardToken] -= reward;
```

Dispute resolutions (`resolveDispute`, `escalateDispute`) also deduct from the same escrow (challenger rewards at 20% of `rewardRate`). If multiple disputes are upheld for a project, the escrow can be depleted below what's needed for remaining validator settlements.

When this happens, `settleValidator` reverts on arithmetic underflow (Solidity 0.8), permanently locking affected validators' in-flight stake. This contrasts with the dispute resolution code which includes explicit M-04 underflow guards.

**Evidence:**
- `QualityEngine.sol:794-795` — No underflow guard
- `QualityEngine.sol:981-985` — Dispute code HAS the guard (inconsistency)

**Fix:** Add the same underflow guard pattern used in dispute resolution: check `projectEscrow >= reward` and cap the deduction at the available balance.

## Medium Severity Findings

### M-01: N-1 Validator Collusion Slashes Honest Validator
**ID:** SEC-COLLUSION-003

Outlier detection in ConsensusLib uses deviation from the weighted average. If N-1 colluding validators submit the same score, they define the average and standard deviation. The honest validator's score becomes an outlier, triggering stake slashing (10-100% depending on deviation tier).

With `numberOfValidations = 3`, only 2 colluding validators are needed to slash the third. The economic incentive exists: colluders earn a larger reward share (the honest validator's weight is excluded from `totalAccurateWeight`).

**Fix:** Enforce minimum `numberOfValidations >= 3` (already partially addressed by M-02). Consider disabling outlier slashing for projects with fewer than 5 validators.

### M-02: Single Validator (numberOfValidations = 1) Has Total Control
**ID:** SEC-SINGLE-VAL-004

With `numberOfValidations = 1`, a single validator determines all outcomes. Standard deviation is 0, so no outlier detection is possible. The validator faces zero slashing risk and earns the full validator reward share.

**Fix:** Enforce `numberOfValidations >= 3` at the protocol level.

### M-03: Dispute Auto-Escalation Favors Attacker When Operator Is Unavailable
**ID:** SEC-ESCALATE-005

If the operator (OPERATOR_ROLE) fails to resolve a dispute within 7 days, anyone can call `escalateDispute` to auto-uphold it. An attacker who times disputes during operator unavailability (maintenance, key rotation, etc.) receives bond refund + 20% challenger reward at zero risk.

**Fix:** Add an `acknowledgeDispute` function that extends the resolution deadline. Consider making auto-escalation reject (not uphold) by default.

### M-04: Claim Hoarding Griefing With Zero Stake
**ID:** SEC-GRIEF-CLAIM-006

When `minStakeToClaim = 0`, an attacker can claim all available project slots at zero cost and hold them for the full 7-day claim deadline. On expiry, the attacker is "slashed" 0 tokens. Legitimate contributors are blocked.

**Fix:** Enforce a protocol-level minimum contributor stake floor.

### M-05: Originator Report Spam Freezes Project Claims
**ID:** SEC-REPORT-FREEZE-007

An open originator report blocks all new claims. At default bond of 1% of `totalRewards`, an attacker can freeze a project for up to 7 days for a relatively small cost. After the report is rejected, the attacker can immediately file again.

**Fix:** Add a cooldown period after rejected reports. Escalate bond for repeated reports.

## Low Severity Findings

### L-01: Non-Upgradeable ReentrancyGuard in Proxy Contract
**ID:** SEC-INHERIT-008

QualityEngine imports `ReentrancyGuard` (non-upgradeable) instead of `ReentrancyGuardUpgradeable`. With Solidity ^0.8.30, OpenZeppelin 5.x uses transient storage (EIP-1153) for the reentrancy flag, making this functionally safe. However, it violates the upgradeable contract best practice.

### L-02: consensusAlgorithm Address Stored but Never Used
**ID:** SEC-DEADCODE-009

The `setConsensusAlgorithm` admin function writes to storage, but `computeConsensus` uses `ConsensusLib.calculate()` directly. The pluggable consensus algorithm feature from the spec is not implemented. This is dead state and dead code.

### L-03: Validation Adapter Fee Not Implemented
**ID:** SEC-VALFEE-010

The spec describes three fee layers (origination, contribution, validation), but `settleValidator` does not deduct a validation adapter fee. The `setValidationFee` admin function exists but has no effect. Validation adapters receive no compensation.

### L-04: Single Dispute Slot Per Contribution
**ID:** SEC-DISPUTE-SLOT-011

Only one dispute can be active per contribution. A weak or malicious dispute filed first consumes the slot. If rejected, the challenge period may have expired, blocking legitimate disputes.

### L-05: Commit Hash Not Context-Bound
**ID:** SEC-COMMIT-HASH-012

The commit hash is `keccak256(abi.encodePacked(score, salt))` without binding to `projectId`, `index`, `nonce`, or `validator`. While storage isolation prevents direct exploitation, validators using the same score/salt across contributions produce identical hashes, enabling correlation analysis.

## Positive Observations

The protocol demonstrates several strong security practices:

1. **Fee-on-transfer handling (M-02):** `fundProject` measures actual received tokens via balance diff
2. **ERC-4626 inflation mitigation:** `_decimalsOffset()` returns 3, adding 1000 virtual shares
3. **Checks-Effects-Interactions:** State updates consistently precede external calls
4. **SafeERC20:** All token transfers use SafeERC20 wrappers
5. **Reentrancy guards:** Comprehensive `nonReentrant` coverage on all value-bearing functions
6. **Bounded iterations:** Loops bounded by `MAX_NUMBER_OF_VALIDATIONS` (10) and `MAX_CLAIM_QUANTITY` (20)
7. **Nonce invalidation:** Rejection increments nonce, cleanly separating stale from current validation data
8. **Storage packing:** Structs are carefully packed (e.g., Reputation in 1 slot, ValidatorConsensusResult in 1 slot)
9. **Reward rate snapshot:** Anti-sandwich protection via contribution-time rewardRate snapshot
10. **M-04 escrow guards:** Dispute resolution code checks escrow sufficiency before deduction

# Fix Plan — Sapien PoQ v0.5

Ordered by priority. Release blockers first.

---

## Release Blockers (MUST FIX before deploy)

### 1. SEC-SETTLE-001 — Validator in-flight stake locked on rejection
**Effort:** Medium (1-2 days)
**Owner:** Core team

**Recommended approach (Option C — least invasive):**

Add a `settleValidatorOnRejection` function:

**Alternative (Option A — more complete):**
- Add `report.finalized` flag separate from `report.computed`
- Set `finalized = true` for both accepted and rejected outcomes
- Change `computeConsensus` guard to `if (report.finalized) revert`
- Change `settleValidator` guard to `if (!report.finalized) revert`
- This allows the existing `settleValidator` to handle both paths

### 2. SEC-ESCROW-002 — Escrow underflow in settleValidator
**Effort:** Small (< 1 day)
**Owner:** Core team

Add underflow guard:

```solidity
// In settleValidator, replace:
$.projectEscrow[projectId][proj.rewardToken] -= reward;

// With:
uint256 available = $.projectEscrow[projectId][proj.rewardToken];
if (reward > available) {
    reward = available;  // partial reward
}
if (reward > 0) {
    $.projectEscrow[projectId][proj.rewardToken] -= reward;
}
```

## High Priority (fix before mainnet)

### 3. SEC-GRIEF-CLAIM-006 — Claim hoarding with zero stake
**Effort:** Small (< 1 day)

Add a global minimum stake floor in `claimToContribute`:
```solidity
uint256 globalMinStake = $.minContributorStake; // new storage field
uint256 stakeRequired = proj.minStakeToClaim > globalMinStake
    ? proj.minStakeToClaim * quantity
    : globalMinStake * quantity;
```

### 4. SEC-SINGLE-VAL-004 — Single validator control
**Effort:** Small (< 1 day)

Change the validation bound:
```solidity
if (config.numberOfValidations < 3 || config.numberOfValidations > MAX_NUMBER_OF_VALIDATIONS) {
    revert InvalidProjectConfig("numberOfValidations out of range");
}
```

### 5. SEC-COLLUSION-003 — Validator collusion
**Effort:** Medium (research needed)

Short-term: document the risk and recommend `numberOfValidations >= 5` for high-value projects.
Long-term: implement Schelling-point mechanisms or commit to a reference answer.

## Medium Priority (fix in v0.6)

### 6. SEC-ESCALATE-005 — Auto-escalation risk
**Effort:** Medium

Add operator acknowledgment mechanism:
- `acknowledgeDispute(projectId, index)` extends deadline by 7 more days
- Only one extension allowed per dispute
- Ensures operator has seen the dispute even if resolution takes time

### 7. SEC-REPORT-FREEZE-007 — Report spam
**Effort:** Small

Add cooldown after rejected reports:
```solidity
if (report.status == OriginatorReportStatus.Rejected &&
    block.timestamp < report.resolvedAt + 7 days) {
    revert ReportCooldownActive();
}
```

### 8. SEC-VALFEE-010 — Missing validation adapter fee
**Effort:** Medium

Implement validation adapter fee in `settleValidator`, mirroring the contribution adapter fee pattern.
