 # Sapien PoQ v0.5 — Security Audit Report

**Branch**: `v0.5-dev` (commit `66b1d81`)
**Date**: 2026-02-15
**Scope**: `src/QualityEngine.sol`, `src/StakeVault.sol`, `src/libraries/ConsensusLib.sol`, `src/Types.sol`, all interfaces
**Pipeline**: Full 13-agent pipeline per `docs/skills/pipeline.md`

---

## Executive Summary

The Sapien PoQ v0.5 architecture is a well-designed consolidation from 5 contracts into 2 contracts + 1 library (QualityEngine, StakeVault, ConsensusLib). The ERC-7201 namespaced storage, phased finalization, and commit-reveal validation are sound architectural decisions.

However, this audit identified **3 Critical**, **5 High**, **6 Medium**, and **8 Low** severity findings. The critical findings — vault share transfers bypassing all stake locks, a `bytes32(0)` commit hash DoS, and zero-stake free-option validation — each independently undermine the protocol's economic security model. Additionally, an escrow insolvency design bug means the protocol cannot fully pay out both contributor and validator rewards when `validatorRewardBps > 0`.

**Gate Status: FAIL** — Release blocked until Critical and High findings are resolved.

## Critical Findings

### C-01: ERC-7201 Storage Location Hashes Unverified

**Location**: `QualityEngine.sol:173-174`, `StakeVault.sol:48-49`

**Description**: The hardcoded `ENGINE_STORAGE_LOCATION` and `STAKE_VAULT_STORAGE_LOCATION` constants claim to be derived from `keccak256(abi.encode(uint256(keccak256("sapien.storage.<Name>")) - 1)) & ~bytes32(uint256(0xff))`, but the values look suspiciously "clean" (not random enough for a keccak output). No on-chain or test verification exists.

**Impact**: If the hashes are incorrect:
- All existing state is stored at an arbitrary slot. The protocol works internally (reads and writes the same wrong slot), but any tooling relying on ERC-7201 derivation sees wrong data.
- A future upgrade that fixes the hash would WIPE ALL STATE — projects, claims, escrow, reputation lost.
- Potential collision with OZ internal namespaced slots.

**Recommended Fix**: Add a Foundry test verifying the constants match the derivation formula. If they don't match, fix them BEFORE deployment.

```solidity
function test_storageSlots() public pure {
    bytes32 engine = keccak256(abi.encode(uint256(keccak256("sapien.storage.QualityEngine")) - 1))
        & ~bytes32(uint256(0xff));
    assertEq(engine, QualityEngine.ENGINE_STORAGE_LOCATION);
}
```

### C-02: Vault Share Transfers Bypass All Lock Mechanisms

**Location**: `StakeVault.sol` — missing `_update` override

**Description**: StakeVault inherits ERC4626 (which inherits ERC20) but does **not** override `_update` to restrict share transfers. A user with locked stake (contributor locks, validator capacity, in-flight) can transfer their vault shares to a fresh address with zero locks, then redeem the full balance.

**Impact**:
1. **All economic security negated**: Contributor slashing, validator slashing, dispute bonds, and originator stakes can all be circumvented by transferring shares before penalties are applied.
2. **Slashing bricks**: After transferring shares away, `_burnShares` reverts (insufficient balance), blocking `slashContributor`, `slashValidator`, `resolveDispute`, `expireClaim`, and `settleValidator`.
3. **Protocol-wide DoS**: A single validator who transfers shares can permanently block consensus settlement for their contribution.

**Exploit Scenario**:
1. Validator commits to validation with 100 token stake
2. Validator `transfer()`s all vault shares to address B
3. Validator submits garbage → marked as outlier
4. `settleValidator` → `vault.slashValidator` → `_burnShares` → **reverts** (0 shares to burn)
5. All other validators' settlements for this contribution are also blocked

**Recommended Fix**: Override `_update` in StakeVault:

```solidity
function _update(address from, address to, uint256 value) internal override {
    if (from != address(0) && to != address(0)) {
        StakeAccount storage acct = _getStakeVaultStorage().accounts[from];
        uint256 totalLocked = acct.contributorLock + acct.validatorCapacity + acct.inFlight;
        uint256 lockedShares = convertToShares(totalLocked);
        require(balanceOf(from) - value >= lockedShares, "Transfer exceeds unlocked shares");
    }
    super._update(from, to, value);
}
```

### C-03: `bytes32(0)` Commit Hash Bypasses Duplicate-Commit Check

**Location**: `QualityEngine.sol:521`

**Description**: The duplicate-commit guard checks `commitHashes[...] != bytes32(0)`. If a validator submits `commitHash = bytes32(0)`, the storage value after write is still `bytes32(0)`, so the guard never triggers. Combined with `stakeAmount = 0`, this is a zero-cost attack.

**Impact**: An attacker can call `commitValidation` repeatedly with `bytes32(0)`, filling all `numberOfValidations` slots. Since `bytes32(0)` never matches a valid reveal hash, the contribution can **never** reach consensus. After `cancelExpiredCommitment`, `validationClaimCount` is not decremented (H-01), making the blockade permanent.

**Recommended Fix**:

```solidity
if (commitHash == bytes32(0)) revert InvalidCommitHash();
```

## High Findings

### H-01: Missing `validationClaimCount` Decrement in `cancelExpiredCommitment`

**Location**: `QualityEngine.sol:819-851`

**Description**: When a ghost validator's expired commitment is cancelled, `commitHashes`, `commitTimestamps`, and `committedStakes` are cleared, but `validationClaimCount` is NOT decremented. New validators cannot fill the vacated slot because `claimCount >= numberOfValidations` still holds.

**Impact**: Contributions become permanently stuck if enough validators ghost. Even a single ghosted validator on a `numberOfValidations = 1` project bricks that contribution entirely.

**Recommended Fix**: Add `$.validationClaimCount[projectId][index][nonce]--;` to `cancelExpiredCommitment`.

### H-02: Escrow Insolvency — Validator Rewards Are Additive, Not Carved

**Location**: `QualityEngine.sol:741-754` (settleValidator), `QualityEngine.sol:785-797` (releaseContributorReward)

**Description**: The contributor receives `rewardRate = totalRewards / totalQuantity`. The validator receives `(totalRewards * validatorRewardBps * weight) / (BPS * totalQuantity * totalAccWeight)`, which sums to `rewardRate * validatorRewardBps / BPS` per contribution. These are **additive** — not carved from the same pool.

With `validatorRewardBps = 2500` (25%), total payout per index = `rewardRate * 1.25`. Over all indices, the protocol promises `totalRewards * 1.25` but the escrow only holds `totalRewards`.

**Concrete Example**: 1000 tokens, 10 slots, 25% validator reward → contributor payouts = 1000, validator payouts = 250, total = 1250 > 1000 escrow.

**Impact**: The last contributors/validators to claim will find the escrow empty. `releaseContributorReward` or `settleValidator` will revert with arithmetic underflow.

**Recommended Fix**: Either:
1. Contributor receives `rewardRate * (BPS - validatorRewardBps) / BPS` (validator share carved out), OR
2. Increase escrow funding requirement in `fundProject` to account for validator rewards.

---

### H-03: `consensusSettled` Not Keyed by Nonce

**Location**: `QualityEngine.sol:133`, `QualityEngine.sol:701`

**Description**: `consensusSettled[projectId][index][validator]` is keyed by `(projectId, index, validator)` without the nonce. When a contribution is rejected and the index is re-submitted (nonce increments), a validator who participated in the old nonce and settled is still marked as `settled = true`. If they participate again in the new nonce, `settleValidator` will revert with `AlreadySettled`.

**Impact**: Validators cannot participate in re-validations of the same index after rejection. This reduces the pool of available validators for resubmitted contributions.

**Recommended Fix**: Key `consensusSettled` by nonce: `consensusSettled[projectId][index][nonce][validator]`.

---

### H-04: No Unlock Path for Validator Capacity

**Location**: `QualityEngine.sol` — missing function

**Description**: `setValidatorCapacity` calls `vault.lockValidatorCapacity`, but there is NO function in QualityEngine that calls `vault.unlockValidatorCapacity`. The vault requires `ENGINE_ROLE` for unlock, so validators can never reduce their committed capacity.

**Impact**: Once validator capacity is locked, that stake is permanently trapped. Validators cannot withdraw it, reduce their commitment, or exit the protocol.

**Recommended Fix**: Add a `reduceValidatorCapacity(uint256 amount)` function.

---

### H-05: Zero-Stake Validators — Free Option Attack

**Location**: `QualityEngine.sol:530-532`, `ConsensusLib.sol:44-46`

**Description**: `commitValidation` allows `stakeAmount = 0`. In ConsensusLib, zero-stake validators get `weight = 1` (minimum floor). They influence consensus, can earn rewards proportional to their weight, but face zero slashing risk (`slashAmount = 0% of 0 = 0`).

**Impact**: Validators can participate risk-free. With `numberOfValidations = 3`, three zero-stake validators can collude to accept/reject any contribution with no economic consequence.

**Recommended Fix**: Enforce a minimum validation stake, either per-project or globally:

```solidity
if (stakeAmount < proj.minValidationStake) revert InsufficientStake(...);
```

## Medium Findings

### M-01: Validator Adapter Fee Not Deducted from Escrow

**Location**: `QualityEngine.sol:745-754`

The adapter fee is credited to `pendingRewards[adapter]` but NOT deducted from `projectEscrow`. Compare with `releaseContributorReward` (line 797) which correctly deducts the full pre-fee amount. Currently unreachable because `validationAdapter` is never populated (M-06), but becomes exploitable if the feature is completed.

**Fix**: `$.projectEscrow[projectId][rewardToken] -= originalReward;` (full amount before fee split).

### M-02: Fee-on-Transfer Token Accounting Bug

**Location**: `QualityEngine.sol:fundProject:280`

`safeTransferFrom(msg.sender, address(this), amount)` — if the token charges a transfer fee, the contract receives less than `amount` but credits `projectEscrow` based on `amount`.

**Fix**: Measure actual received: `uint256 received = balance_after - balance_before`.

### M-03: No Project Completion or Escrow Refund

**Location**: `Types.sol:12` — `ProjectStatus.Completed` is defined but never set

No function marks a project as Completed, refunds remaining escrow dust to the originator, or unlocks `originatorLockedStake`.

**Fix**: Add `completeProject()` that verifies all indices are settled and returns remaining escrow.

### M-04: Dispute Resolution Can Revert on Escrow Underflow

**Location**: `QualityEngine.sol:resolveDispute:934-938`, `escalateDispute:999-1004`

Challenger reward is deducted from escrow without an underflow guard (unlike the rejected-contribution path at line 945 which checks `>=`).

**Fix**: Add `if (challengerReward > 0 && $.projectEscrow[...] >= challengerReward)` guard.

### M-05: No Timelock on Admin Operations

**Location**: Both contracts — `_authorizeUpgrade`, all `set*` functions

No timelock on UUPS upgrades, fee changes, or treasury redirection. A compromised admin key results in immediate total fund loss.

**Fix**: Deploy behind a TimelockController with 48h minimum delay on upgrades, 24h on parameter changes.

### M-06: `validationAdapter` Mapping Never Populated

**Location**: `QualityEngine.sol:147`, `QualityEngine.sol:745`

The mapping is declared and read in `settleValidator` but never written to. `commitValidation` has no `adapter` parameter.

**Fix**: Either add an adapter parameter to `commitValidation` or remove the dead code.
